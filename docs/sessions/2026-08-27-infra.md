# 2026-08-27 — `infra`: a run that never happened, and the copy that could not tell

The daily job stopped running and nothing noticed. I set out to build a recovery cron and a
watchdog. **The measurement and three adversarial waves killed both**, and what shipped
instead is the delivery defects that were real that morning — all inside existing named
steps, so `36 of 80` never moved and no other lane's document had to change. Wave 3 then
found eleven more, nine of them in the code I had just written (section 4b).

## 2. `last_run.json` is not a symptom of the same thing

`persist_state.py`: `healthy = job_status == "success" and not failed_steps; if healthy:
return 0`. The file is written **only when a run was unhealthy**, so `2026-08-25` on
2026-08-27 means *no digest has failed since 08-25* — correct, not stale. And
`_last_run_alarms` returns `[]` on a healthy record **before** it computes an age, so the
date could be a year old and nothing would degrade. It is also not what says *"yesterday's
digest never completed"*; that is `stages.alarms("publish", 1)`.

BACKLOG `294@infra` was wrong on both halves and is closed as such; `224@infra` asked the
same question more carefully and is closed with the answer.

**What was real is the name.** A file called `last_run.json` that records only the last
*unhealthy* run is heartbeat-shaped and is not a heartbeat — it misled two backlog items and
one document, and it is the first thing anyone building a watchdog reaches for. That is what
`cloud_state/last_delivered.json` is for.

## 3. What I rejected, and why

### The recovery cron — rejected on measurement, deferred for re-measurement

`tests/schedule_census.py` counts **isolated single-slot drops**: a slot missed while its
neighbours fired, which is the only shape a second cron can rescue. **The count is 0.** Every
drop in the repository's history belongs to one correlated event spanning eight hours and
two repositories.

The tool's first draft reported **four** isolated drops — every one of them
`firmographics 10:00` on days before that workflow existed. It would have answered its own
pre-committed question with an artefact. `cron_since()` now scores a slot as due only from
the moment its cron string reached the branch, and the count went to 0. That near-miss is
the reason the falsifier is written into the tool's output rather than into a paragraph:

> **≥ 3 isolated single-slot drops ⇒ build the recovery cron. Otherwise it stays rejected.**
> Due 2026-09-10.

Two design attacks found four more reasons independently: `actions/checkout` resolves
`github.sha` when the RUN is created, so a queued recovery holds a stale tree and re-emits
roles; the guard predicate's false positive on `digest.py`'s render stub would suppress
recovery for the *most* recoverable failure there is; and a 07:41 slot plus a 110-minute
pipeline budget lands past the relay's 10:17 cutoff, manufacturing `6@infra`.

### The watchdog — rejected as actively dangerous

`digests/latest.md` is `SINGLE_WRITER: daily-digest`. Its conflict rule is `s_ours` ("the
run's own bytes win") and `merge_conflicted` suppresses the overwrite warning for exactly
those paths. A watchdog deciding "no digest" at 09:43 while a late digest commits at 09:44
loses the push race and writes its notice **over a delivered digest whose roles are already
marked sent** — turning a late day into a permanently lost one. `160@infra` says this in
advance: the unit guard cannot catch a second writer of an `ours` path, only a reviewer can.

The "elegant reuse" I had planned was also a silent no-op: `notice_warranted()` returns
`False` for a watchdog's empty `STEPS_JSON`, so `outcome --commit` would have written no
notice at all.

Filed as `304@infra`: the safe home is the relay repo, which already holds the notification
credential and already fetches the file.

## 4. What shipped

The pipeline step's last line was `cp out/digest-$(date -u +%F).md digests/latest.md`. That
one line carried three failures; it is now `python persist_state.py deliver`.

1. **A THINNER digest never replaces a fatter one.** `filter_new` drains `sent`, so a
   second same-day run renders fewer — often zero; the `cp` put that over the real digest
   and the relay would have mailed the thin one, whose missing roles are already marked sent
   and never come back. Weakness is measured against the receipt, not against zero (wave 3).
   It is also what makes an operator re-run safe, which the recovery cron would have needed.
2. **Past the relay's last poll the roles carry to tomorrow instead of burning.** `deliver`
   withholds `DIGEST_JSON`, and the `mark_sent` step is *already* guarded on it, so that
   step needed no edit at all. **Break-glass:** after two mornings with no delivery it
   delivers anyway — a cutoff that fires every day would defer for ever, and the alarm for
   that lives in the mail it is deferring.
3. **It reads origin, not its own checkout** — the stale-`github.sha` attack.
   `tests/rehearse_infra.py --twice` replays it against real temp repos: the morning run
   delivers 8 roles and pushes, a second run whose clone predates that push renders 3, and
   origin keeps the real digest with `DIGEST_JSON` never exported.
4. **`cloud_state/last_delivered.json`** — the receipt, staged by the same persist step and
   restored with it when a gate fails, so it cannot outlive the file it describes. `daily-digest` is the only workflow that
   owns `cloud_state` as a directory, so it has exactly one writer. Seeded from the file
   origin actually carries (2026-08-26, 8 roles, sha verified), which means the next mail
   will correctly say `the last digest that reached the mail was 2026-08-26 (2d ago) — 1
   morning(s) produced no email`.

Plus one clock: `run.py`'s default `run_date` moved from local `date.today()` to UTC, since
the workflow, the H1, `deliver` and the relay all compare against it.

**Cost: zero.** No new workflow, no new cron, no new named step — `36 of 80` unchanged, so
no `coe_ratio` edit in `CLAUDE.md`, `ARCHITECTURE.md` or `docs/AGENT_BRIEF.md`.
`tests/schedule_census.py` lives beside `rehearse_infra.py` for the same reason: a lane
harness in `tests/` is not a root module, so `root_py_count` and `unreferenced_roots` — both
registered in `docs`-lane files — did not move either.

## 4b. Wave 3: three Opus attackers on the real diff, before the push

Everything in section 4 above shipped only after this. All three ran read-only against the
committed branch; none was pointed at my worktree. **Eleven defects, nine of them in code I
had just written and called finished**, each reproduced by the attacker rather than argued:

| what they broke | why it mattered |
|---|---|
| `git_ok("fetch", ...)` return **discarded** | `actions/checkout` leaves `refs/remotes/origin/<b>` at the run-creation sha, so a failed fetch makes `git show origin/…` SUCCEED on exactly the stale view the guard exists to distrust — and the log still said `origin`. Reproduced as an empty digest replacing the morning's mail. One unchecked bool disarmed the whole change. |
| `weak_digest` was **absolute** | A stale re-run rendering 3 roles where the morning had 8 sailed past `roles <= 0`; the other five are already `sent`, so they are never mailed, ever. Weakness has to be relative to the receipt. |
| the receipt was read from the **checkout** | while `latest.md` was read from origin. A three-day-old tree opened break-glass on a day that had already delivered. |
| **future-dated receipt** | negative staleness read as "fresh", so the cutoff never opened AND `_receipt_alarms` stayed silent: indefinite, total, green-run mail loss. |
| break-glass **marked roles sent** | a digest written past the last poll is overwritten by tomorrow's run before tomorrow's first poll — so it burned roles that were never mailed, which is the exact loss deferral exists to prevent. It now writes the file and marks nothing. |
| **`s_ours` returned `ours` unconditionally** | so `deliver` refusing to overwrite origin's fresh digest was *overturned one step later*: the persist step's conflict path pushed the run's checkout-era copy back over it, silently, because the overwrite warning is suppressed for `SINGLE_WRITER` paths. This is BACKLOG `160@infra` live. Fixed generally: a run whose bytes equal the base never wrote the file and has no opinion about it. |
| the **receipt could outlive its digest** | `run_gates` restores one failing path and lets the rest push, so origin could carry a receipt for a digest that is not there — and `_receipt_alarms` would then trust it and hide the lost morning. They are now restored as a pair, and the alarm checks the receipt's sha256 against the file. |
| **"these roles lead the next digest" was false** | `run.py` selects the mail with `get_matched_since(today - 1 day)` — a two-bucket window that MOVES. A role first seen yesterday and not mailed today is outside it tomorrow and for ever: on the board, unmarked, unreachable. Pre-existing (`build_notice` has said it since 08-25) but deferral made it routine. `deliver` now COUNTS the split instead of asserting the happy version; the real fix is `roles` lane's (BACKLOG `309@roles`). |
| `--ignore-cutoff` was **unreachable from the cloud** | `workflow_dispatch: {}` declared no inputs. A documented escape hatch that does not exist is this repo's signature failure. |
| `outcome` still on the **local clock** | the one caller the UTC fix missed, while `deliver` now compares dates against it. |
| env vars parsed at **import** | a typo in `DELIVER_MARGIN_MIN` would have taken `commit` and `outcome` down with `deliver`. |

The census tool did it to itself too: its first draft reported **four** isolated drops, every
one `firmographics 10:00` on days before that workflow existed — it would have answered its
own pre-committed question with an artefact. `cron_since` fixed that; then an attacker showed
the fix's default case (`born is None`) scored an *uncommitted draft* for the whole window and
produced **seven** fabricated drops, i.e. it failed toward "build the cron". An undatable cron
is now skipped with a loud warning.

Every one of these has an assertion in `tests/test_units.py`, and every assertion was
mutation-checked: the fix reverted, the guard observed to fail, the fix restored.

## 4c. Wave 4: pointed at the gap wave 3 left, and it found a shipped outage

Wave 3 reviewed the code *before* the `s_ours` change and *before* the workflow edit, so
those two shipped unreviewed. Wave 4 was aimed at exactly that. It found **one defect that
would have broken production every single day**:

> `daily-digest.yml` line 161 was ONE physical line with a literal backslash-n where a
> continuation was meant. bash reads the `n` as an argument, `persist_state.py` exits 2, the
> `pipeline` step (not continue-on-error) goes red, **the board never publishes and the mail
> becomes a failure notice** — daily, for ever.

Two attackers found it independently. It was **syntactically valid**, so a `bash -n` guard
passes it — my first attempt at a guard did exactly that. The guard that works tests INTENT:
a backslash-n outside quotes anywhere in a workflow is a faked continuation.

And it broke the `s_ours` change I had shipped with no adversarial review at all:

| found | why it mattered |
|---|---|
| **abstention adopted a BROKEN origin copy** | the old unconditional `ours` was, incidentally, the only self-heal origin had for the 16 `SINGLE_WRITER` paths. With my change, a corrupt copy on origin is adopted, re-gated against itself, restored from itself, and the step exits 1 **every night for as long as the owner keeps abstaining**. Reproduced against `telegram_seen.json`. Healing is now deliberate (`_well_formed`). |
| **`weak_digest` was dead code on the run that mails** | it only ran behind `on_origin`, which is False on a normal morning. So on the one run per day that actually mails, `deliver` validated *nothing*: a zero-byte file, a body-less heading, and yesterday's digest under today's name all went through. |
| **`PAIRED` was two-way** | a corrupt receipt withdrew a good digest — after `mark_sent` had already burned its roles. It is one-way now, and an unrestorable mate is removed rather than silently shipped alone. |
| **a thinner-than-origin refusal was quiet** | `publish` is gated only on the pipeline step, so exit 0 shipped that same thin run's board to the public repo while origin kept the fat digest. Only the cutoff deferral is quiet now. |
| **break-glass silenced its own alarm** | a write past the last poll still stamped today on the receipt, so the next day read `age 1` and went quiet — a chronically-late pipeline could alternate defer/break-glass for ever at zero mail. The receipt carries `past_cutoff` now. |
| **the receipt's sha was the CRLF one** | I seeded it from a Windows checkout: `0a3aa0fa…` against the blob's `71ef0dcb…`. The fingerprint is EOL-normalised now, and pinned. |
| **`_carry_note` printed a wrong number** | it counted `first_seen` only, and said `20 of 20 role(s) lead the next digest` on a day when none did. It now counts what tomorrow actually tests. |
| **a junk `roles` field crashed the day** | unguarded `int()` on a receipt field → exit 1 → the whole day a failure notice. |
| my own **over-claims** | ARCHITECTURE said the pairing meant origin "can never" carry an orphan receipt, and the code cited BACKLOG 160 as "closed". Neither was true; both corrected. |

**And I made the mistake I had warned the attackers about**: a `git checkout -- pipeline/run.py`
to undo a mutation test reverted three real edits with it. Recovered, but the rule is the
rule — use a backup copy, never `git checkout --`, on a file with uncommitted work.

## 5. Is a permanently-red required check an infra problem?

`tests.yml`: **42 runs since 2026-08-25T16:00, 40 `failure`, 0 green.** The assertion is
`test_a_role_is_filled_from_another_address_it_was_seen_at` (`assert 170 == 2021`), a
`jd-text` guard that reads the live scrape cache which a cron then rewrites. Not mine, not
touched.

The *contract* is infra's. `CLAUDE.md` promises `pytest` green before any push, and for two
days every lane has pushed over red — which teaches every lane that red is normal, the exact
failure this repo punishes hardest. The defect class is *a unit test that reads mutable
production state*, and a guard for it is one assertion in this lane's own block. Filed as
`306@infra` and deliberately not written: a new failing guard on top of 40 red pushes helps
nobody.
