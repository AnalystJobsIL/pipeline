## Why my three failed, verified rather than assumed

The checks skip when `GITHUB_ACTIONS` is set — deliberately, because a runner's checkout is
one commit deep and "how far behind is this tree" has no answer there. My fixtures cleared
that variable from the **git subprocess environment** and never from the **pytest process the
check runs in**. So on a runner every one of them got an empty error list and asserted
against it.

Reproduced both ways before fixing: `GITHUB_ACTIONS=true python -m pytest -k "checkout_left
or checkout_behind or scheduled_workflow_change"` fails on this laptop exactly as it does on
the runner, and passes with the fix. That is the whole bug — a variable cleared in the wrong
process — and it is the same shape as everything else this week: **I verified in one
environment and reported for another.**

## The three guards now run in CI, and CI now checks my reasoning

`_not_ci` (a context manager in `tests/test_units.py`) clears the variable from the pytest
process for the duration of a check call. Three call sites use it.
`test_the_tree_check_is_silent_in_ci_and_never_fetches` deliberately does **not**: skipping in
CI is the design, and asserting on the skip is not the same as never exercising the check.

The *checks themselves* still skip on a runner, and that reason is now **observable and
verified rather than documented**:

* `_tree_skip_reason()` returns the reason in words. `python docs/check_docs.py --tree` prints
  `tree: no reading here - CI: the runner builds the pushed commit from a depth-1 checkout…`
  instead of a shrug.
* `test_ci_itself_confirms_why_the_tree_check_cannot_run_there` runs **only on a runner**. It
  asserts that either there is no `origin/master` ref or the history is one commit deep, and
  emits `CI checkout: shallow=… origin/master=… commits=…` as a **warning**, because pytest
  shows a passing test's stdout only under `-rP` — as a `print` the facts would have been
  visible exactly when they were not needed. If `actions/checkout` ever changes its
  defaults, the build says so instead of the documentation quietly becoming false. Verified
  it is not vacuous: handed a full clone while claiming to be CI it **fails**, reporting
  `shallow='false' origin/master='7ac03d08' commits='606'`.

**They are still local-only guards, and that is now written down rather than implied.** A
morning check due **2026-09-06** asks the question that matters: has any of the three actually
stopped a lane in a week? If not they are decoration, and the row says to file them as such.

## `coe_ratio`: the fix, and the design question underneath it

Fixed the number, then removed the class of failure. It is now a one-sided **floor** —
`coe_steps`, census class, `44+` at all four sites — reusing the machinery the census facts
already have.

Three options, and why this one:

* **Keep the exact pin and fix it each time.** Rejected on measurement, not taste. It broke
  within a day of being pinned, and when it broke it did not merely annoy: `Registry
  invariants` and the fourteen rehearsed nights are steps **below** `Unit guards` in the same
  `tests.yml` job, so a red suite **skips** them. A stale number in a brief switched off the
  registry gate — the exact failure the census floors were introduced to stop, which this
  file's own comments already argue at length.
* **Drop the number, print a command.** Rejected. The number *is* the rule — "a green
  workflow means nothing" — and a rule whose evidence is a command nobody runs is a rule
  nobody believes. The repo took this option for the API/page split because no decision turns
  on that number; a decision turns on this one every time an agent reads a green run.
* **A floor on the count.** Taken. Steps are added most weeks and a floor absorbs every
  addition. It fires only on a **collapse** — the case where `continue-on-error` became rare,
  the rule above it stopped being true, and a human must rewrite it that day.

The denominator leaves the pinned text: it was the half that moved most and the half no
reader acts on. `test_the_continue_on_error_number_is_a_floor_and_never_a_pin_again` pins the
*decision*, with the skipped-registry-gate argument in its docstring, so the next session that
wants to "tighten" it reads why first.

## The CI-truth clause

`docs/AGENT_BRIEF.md`'s definition of done and `CLAUDE.md`'s contract item 1 now say that
**`pytest` green means green in CI, on the commit you pushed** — `gh run list --workflow
tests.yml --limit 1`, the sha must be yours, the conclusion `success`, and **the run id goes
in the `HANDOFF.md` line**. A red run is yours to fix or revert whoever made it red; if it was
already red when you arrived, say so with the run id so the next session knows what it
inherited.

It is the sibling of yesterday's production clause. That one says an exit code is not a
result; this one says a result on your machine is not a result on the runner. Both exist
because 100 consecutive red runs went unmentioned while every lane reported a passing suite.

## The runner corrected me

The reason I wrote for skipping in CI was "a depth-1 checkout has no ref to be behind". The
guard emitted what it actually found, on run **33294213125**:

    CI checkout: shallow='true' origin/master='61bbc99a' commits='1' reason_without_env=None

Half of it was wrong. `origin/master` **does** exist on a runner — it points at the very
commit being built — and `reason_without_env=None` says that with the variable removed the
check would run happily rather than bail out. The true reason is narrower and better:
**`origin/master` IS this commit, so `behind` is 0 by construction**, and a check that can
only ever say 0 is a check that says nothing.

`_tree_skip_reason()` says that now, with the run id beside it, and the guard asserts the
CONSEQUENCE — with the variable gone, `tree_state()` reports 0 behind — instead of the
symptom I guessed at. Verified not vacuous: on a full clone claiming to be CI it fails with
`the checkout is 1 commits behind origin/master`.

That is the exercise in one line. I had a plausible reason, wrote it into three places, and
it took a machine printing what it saw to show that half of it was false.

## Definition of done: the outcome is first now, and every lane has a number

The section was entirely process — tests green, docs updated, a HANDOFF line, an item filed,
and (since yesterday) an unattended run quoted. Every clause was about not breaking things.
A lane could satisfy all of them having drained nothing, and six lanes were optimising for
auditability because auditability was what the finish line asked for.

It now reads: **1. the number moved · 2. it keeps moving without a session · 3. nothing
broke** — with clause 3 labelled the price of admission, and *"reporting this section as the
outcome is the mistake the section exists to stop"*.

**Clause 2 is a delivery bar, not a wish.** The standard is not "the queue reached zero", it
is *"this flows automatically in git from now on"*. A lane whose number falls only while a
session runs has **not delivered**, however far it fell, and says those words. Three things
must be named — the **workflow**, its **cadence** (with the `event: schedule` run that proved
it), and the **alarm**, *where a human reads daily*. Any one missing **is** the lane's
remaining work. If the fix needs a workflow, that is `infra`'s file and the deliverable is
the **exact diff**, filed, plus the sentence *until infra applies it, nothing is automatic*.
