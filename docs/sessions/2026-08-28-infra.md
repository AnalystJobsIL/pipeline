## 1. The relay — and the brief's framing needed correcting

The brief said "the relay has no working scheduler" and "the pipeline side is not the problem
and you should not fix it". The first half is right; the second is not, and conflating them
hides a whole lost morning.

| date | digest artefact | relay polls | mail |
|---|---|---|---|
| 08-26 | `b2090f6` 06:03 | 4 of 4 | issue #10, scheduled |
| 08-27 | **never written** | 1 of 4 | **none, ever** |
| 08-28 | `9bbaf69` 07:08 (hand-dispatched run) | **0 of 4** | issue #11, hand-dispatched |

`git log --date=iso-strict origin/master -- digests/latest.md` jumps from 08-26T06:03 to
08-28T07:08. On 08-27 the digest cron was dispatched at **16:18** (+11 h 18) and `deliver`
correctly refused it as past the relay's last poll. **So 08-27 failed on the pipeline side and
08-28 on the relay side.** The relay's single 08-27 poll behaved perfectly.

**The fix, and why the obvious ones do not work.** `tests/schedule_census.py` measures **0**
isolated single-slot drops — slots fail together — so redundancy *inside* GitHub's scheduler
buys nothing, which is why `292@infra` rejected a watchdog cron and why more relay polls would
not have helped on 08-28. There is no credential-free cross-repo trigger on GitHub, so the
real choice is *which credential and where it points*. Chosen: a **write deploy key**, because
it belongs to a repo rather than a person (no run page names the owner) and cannot expire
silently — a dead PAT would reproduce exactly this failure with no alarm. `daily-digest`'s last
step pushes a receipt carrying the **sha256 of the bytes that actually landed on origin**; the
relay triggers on that push and retries its fetch until what it holds hashes to the receipt,
which is what beats `raw.githubusercontent`'s cache exactly rather than with a sleep.

**Proven:** run `33159616979` in `AnalystJobsIL/inbox`, `event=push`, 8 s after the receipt —
`push event: waiting for the digest that hashes to 5d4a0f8a4256` / `raw is current (attempt 1)`
/ `already posted: … (5d4a0f8a4256)`. **Not proven:** an issue being *created* on a push event,
because today's digest was already mailed and the dedup correctly declined; forcing it would
have sent a duplicate for no information. Filed as a morning check.

**Inert until the operator installs `INBOX_DEPLOY_KEY` and `INBOX_REPO_GIT`** — with either
unset the step prints one line and exits 0. Full reasoning, including the residual identity
risk that is now accepted rather than assumed away, in
`docs/decisions/2026-08-28-relay-trigger.md`.

The step had to go **after** `outcome`, which is what turns a lost morning into a mailed
notice — and a lost morning is when the mail matters most.
`test_daily_digest_steps_have_ids_no_swallows_and_an_outcome_step` asserted `outcome` was
last; it now encodes the new contract and is **stricter**: what follows must write no repo
state and must never fail the job.

## 2. The paid rung

`scrape-refresh.yml:52` set `SCRAPE_VIA_UNLOCKER: "1"` hardcoded, with no input and no cap, on
a nightly cron nobody watches. It bought **72 credits for 10 boards** on 08-28
(`unlock_calls 72 → unlock_ok 63 → unlock_won 10`), a number that lived only in a committed
state file. Three facts made it unbounded rather than merely unwatched: every cap in the repo
is per-**process**; there is no persisted credit ledger anywhere; and the flag arms on any
non-empty value, **including the string `"0"`**.

Operator's decision, settling `192` vs `335`: **no ceiling for the rest of August, 5,000 from
2026-09-01** — August uncapped on purpose, because the pool was already ~6,798 MTD and a 5,000
ceiling is exactly what made `budget_per_day()` return 0 while bought credits sat unused.

Shipped: a `BD_PAID_RUNGS` repo **variable** plus a dispatch input at all five flag sites (off
yields the *empty string*, never `"0"`); `BD_RUN_CAP` enforced in `bd_rescue.unlock_status` —
the one chokepoint ten of the ~thirteen spend paths reach — **defaulting to 0 = unlimited** so
no lane that ignores it changes behaviour; `pipeline/bd_budget.py` holding the dated rule once,
with a guard pinning both sides of 2026-09-01; and the spend printed to the run page.

**`bd_rescue.py` is shared plumbing, so, loudly:** the lanes whose spend now passes a cap are
`scraper` (`scrape_universal`), `registry` (`crack_walled`, `triage_dark`, `repair_dead_urls`,
`resolve_broken`, `deep_validate`, `listing_hunt`, `resolve_llm`, `audit_empty_rows`,
`registry_health`), `discovery` (Indeed/LinkedIn sweeps) and the shared `identity_gate`. None
sees any change unless its workflow sets `BD_RUN_CAP`, and all of them now get a
`[bd-spend]` line per process — the per-workflow measurement that did not previously exist.
The `250`s are a **blast-radius limit, not a budget**; `365@infra` says replace them with the

## 3. The cache rewrite — the diagnosis corrects the brief

**Reproduced exactly**: `61181c1` → `4405397`, 279 → 263 companies, 1,643 → 1,607 postings.
The brief attributed it to the `error != empty` class ("a board briefly unreachable is dropped
as though it were empty"). It is not that. Of the 16 lost boards, **16 of 16 carry
`why=empty`, `found=0`, `http` 200/202** — not one is an error — and **14 of the 16 were on
their first empty night**.

The real defect is an **asymmetry**: an error is carried 14 nights (`CARRY_MAX_DAYS`), a
zero-extraction is authoritative immediately. Nothing saw it because
`refresh_scrape_cache`'s abort needs >20%, `s_company_dict`'s guard needs >25% *and only runs
on a push conflict*, and `check_invariants.py` never opens the cache. 5.7% is invisible to all
three. Same pass: 243 → 219 on 08-26, 221 → 205 on 08-27.

**Sized honestly:** the cron re-scrapes all 496 rows nightly, so a dropped board returns the
next night. This is **oscillation, not cumulative drain** — the cost is roles flickering on and
off the board between mornings. A quality bug, not a coverage leak.

**Mine, shipped:** `persist_state.py` measures every keyed cache against the checkout on every
commit, reports to the **run page first** (the digest alarm line has been invisible for three
days, so it cannot be the primary surface), and appends one line to
`cloud_state/persist_log.jsonl` so tomorrow's run can say what yesterday cost. Threshold
`>= 10 keys AND >= 3%` — fires on all three regressions, quiet for the 1–4-key legitimate
deletions — **provisional on n=3**, re-measure filed as a morning check for 2026-09-11.
**It does not block:** a wrong threshold that froze the cache would cost coverage, which is
what this very day was spent undoing. ARCHITECTURE §5d.

**Theirs:** `363@scraper` is the written specification, aimed at the asymmetry rather than at
"retain on error", with the reproduce command and the 16 names. The mechanism is that lane's
call; `scrape_rot.json` already counts consecutive empties in `n`.
