## C1 — a reject cell withdraws the row (`e395fe6`)

`543` gave the reject map a deliberate refusal: **the status is not touched**, because a
rejected posting stops being upserted and closes tomorrow on the ordinary ladder. It does.
And `closed` is a column value, not a way out of the file — a closed row publishes for the
rest of its 90-day window. That is how 11 rows shipped a NO to readers, which is neither of
the two states the operator's bar allows (IN under the live contract, or excluded with a
written, counted reason).

`Ledger._withdraw_rejected` runs at the end of every `record_run`, over **every record and
not only this run's map** — the eleven cells were stamped days earlier, by runs that judged
the roles while they were still fetched, so a sweep keyed to `class_rejects` would never have
reached the population it was built for. `open`/`closed` + `reject` becomes `withdrawn`,
`withdrawn_by=classifier`, `withdrawn_on=<run date>`,
`withdraw_reason="classifier <path> under <contract>: <the cell's reason>"`, `closed_on` kept
or `last_seen`. **Never `retracted_on`** — that field is a line's, and a record carrying one
with no line is lifted back onto the ladder the next morning by the lift arm.

Reversible by the verdict alone (the orchestrator's ruling): `withdrawn_by=classifier` with a
cell that no longer says `reject` returns the record to `closed`, or `open` if the run put it
back on the board, with the three stamps popped. No hand line in either direction.

**The sweep withdraws 12 records, not 11.** The brief and every count above read the
PUBLISHED file; the ledger holds a twelfth, `madanes insurance agency|manager bi` (closed
2026-09-01, `desc_len` 0), which the 2026-09-01 textless-row policy already excluded from the
CSV. Simulated against `a96ee8a`: 12 withdrawn, `withdrawn` 60 → **72**, dataset **175** rows,
`reject_refused` 0. The difference between 11 and 12 is worth stating rather than discovering
on 09-19.

**Re-simulated after the rebase onto `5673c38`**, which carries the classifier lane's
`37f308a` (7 new retraction lines, 5 of them naming records among my 12). The hand lines run

Three placements I changed from the plan, each because the plan's placement was wrong:

* the sweep runs **after** the mass-close block, not before it. A record with `_close`
  pending has its status rewritten by that block; a withdrawal written above it would end as
  `status: closed` with the withdrawal stamps still on the record.
* the export guard sits **below** the date checks. A corrupt half-written record has no
  verdict cell either, and `unjudged_refused` would have sent a reader to the classifier for
  a record whose real defect is that it has no dates (it broke
  `test_the_export_seam_never_freezes_the_ledger_and_never_raises`).
* the `judged` branch gained `elif prev_status in RETRACTABLE: c[…_total] += 1`. A machine
  withdrawal reaches that branch every morning its company is scanned and was counted
  **nowhere**, so `excluded.withdrawn` would have disagreed with the file it describes.

`build_rows` refuses a `reject` cell — and an empty one, per the orchestrator's answer 3 —
as a **tripwire, not the mechanism**: `reject_refused` / `unjudged_refused`, named in
`reconciliation.identity` so the count still closes against the store, alarmed on `Stages:`.
`removed_list` and `_published_span` read `withdrawn_on` after `retracted_on` and **before**
`closed_on`; falling through to `closed_on` would have published a span ending the day the
posting left its board, weeks before the row left the file. `removed[]` also gained `by`
(`classifier` / `human`), because a downloader reconciling against that list could not
otherwise tell a machine verdict from an adjudication.

`tests/_rec` now carries an accept verdict — **a publishable record is a judged one**, which
is the rule this commit lands — and the four backfill tests that meant "unjudged" say
`class: {}` explicitly. That is a better fixture, not a workaround: the queue those tests
describe IS the verdict-less records.
