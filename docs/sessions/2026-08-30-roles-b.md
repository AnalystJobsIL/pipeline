### The verdict class: `withdrawn`, and why it is not `purged`

`purged` means *the COMPANY was never an employer* (Tel Aviv is a city). Comcast IS an employer;
its Houston POSTING was never ours. Filing that under `purged` would make the meta's one-line
definition false, so `STATUSES` gained `withdrawn` = *the employer is real, THIS posting was
never in scope*. Both leave every product; both keep their line; the meta documents all three
exclusion classes with counts.

### Tombstone, vanish, or list — the decision

Three shapes for the public file. **A tombstone row inside `roles.csv`** (status `withdrawn` +
a reason column) was the orchestrator's instinct and I rejected it: every naive reader —
`pandas.read_csv` then `groupby` — counts Houston as an Israeli analyst role again unless it
knows to filter, and a dataset whose DEFAULT read is wrong is the failure being fixed. **A
silent vanish** leaves a repeat downloader nothing to reconcile. **Chosen:** the row leaves the
CSV; the tombstone lives in the meta's `withdrawn` list (company, title, status, reason, the day
it left, and `published_in_roles_csv: {from, to}`) and in the public `roles.jsonl`, where the
record keeps its line with its status and reason. No fourth file was needed, so nothing waits
on infra for the reconciliation to reach Pages — the meta is already copied there.

`published_in_roles_csv` is derived (the export never writes to the record): `from` = the later
of the file's first day (`DATASET_SINCE = 2026-08-30`) and the record's first sighting, `to` =
the retraction date, **inclusive and conservative** — the 08-30 file shipped before the line
was written, so `to` names the last file that MAY carry the row, never one that certainly does
not. The seven `Tel Aviv` rows get `null`: they left on 08-27, before the file existed, and the
meta now says so instead of implying a withdrawal from a file nobody had.

### The mechanism, and why it is keyed by url

`cloud_state/roles_retractions.jsonl`, one object per line, human-written, committed. Keyed by
**url**: Comcast's `role_id` is `comcast|manager 2 business operations amp analytics` — the
`&amp;` is in the id — so the day scraper unescapes titles a new id is minted and a role_id-keyed
line would silently stop matching while the posting kept coming back. The address is stable.
`roles.Retractions.match` accepts role_id, url, or any `seen_id` (a scrape id IS the url).

It is applied from ONE object in TWO places, the way `_never_ours` already is: `run.py`'s
`_alive` (email + board) and its archive filter read `ledger.retractions` — the FILE, never the
ledger's status, so a frozen-ledger day cannot resurrect Houston — and `Ledger._record_run`
stamps the status BEFORE `rid in onboard`, so a board that keeps listing the posting keeps it
withdrawn. Lifting one is deleting the line. Three alarms: applied (once, naming row and
reason), `roles retraction unmatched (<key>)` for a line no record answers to (a typo must not
read as "applied"), and `roles retractions unreadable (N bad line(s) …)` with the rest of the
file still applied.

### Jobgether did not need a line — three automatic sources

`intake_rejects.json` already said `jobgether: agency` since 08-28; the 08-26 record stayed
because a rejection was never applied backwards — a filter with a hole exactly one day wide.
`_never_ours` is now `{identity: reason}` from three sources, each minus every identity a live
registry row answers to, each under the mass-purge hold: the registry's aggregator rows
(`PURGE_REASON`, unchanged so the seven existing records do not churn), intake's `agency`
verdicts (`PURGE_REASON_AGENCY`: Jobgether, Nogamy, Shavit Software), and
`recruiters.is_recruiter` over the store's names (`PURGE_REASON_RECRUITER`: the nine agencies
BACKLOG 460 (iii) enumerated — Abra, Alpha | Similarweb Partner, Nisha Pro, Recruitx, Yael
Korentec Technologies, comblack ×2, plus the three above). **Measured before shipping: 10
records, every one already `closed`, none at an active row.** 460 (iii) is drained; the
record says which source purged it.

### 90 days, and the archive before the first eviction

`WINDOW_DAYS = 90` with the operator's decision beside it. Nothing is evicted by it:
`roles_archive.csv` is the complement on the date axis (`last_seen < window start`, same 54
