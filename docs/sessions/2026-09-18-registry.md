## 3. The queue alarmed on its own cadence, and a refusal was re-bought for ever (`095e725`)

### 3a. `queue GREW` fired on a lapse wave

The 09-18 stamp, verbatim from `cloud_state/pipeline_stages.json`:

```
queue: owed=28 delta=28 direction=GROWING new_intake=0 selectable=28 capacity=176
       searched_recently=76 ledger_contradicted=3 unverified_rows=12
       alarm=queue GREW by 28 since 2026-09-16 -- the drain is not keeping pace with intake
```

Read the alarm against the numbers beside it: `new_intake=0` — **nothing arrived**; `selectable
28` of `capacity 176` — the night could buy six times what was waiting. The 27 names searched
on 09-04 plus one from 09-03 came due, that is all, and the 09-17 drain had taken its entire
selection set (`queue-resolve-search: 20/19/19/19 names`, no `of N selectable` suffix, which
`main` prints only when selectable > take). `owed` rises for two different reasons and this
alarm could not tell them apart.

It now fires only when `new_intake > 0` **or** `selectable > capacity`. A rise that is neither
reads `direction=lapsed` — a VALUE, not a new key, so every reader of `direction` keeps
working. One thing I got wrong on the first pass and fixed before the commit: the suppression
read an ABSENT `new_intake` as zero. `_drain_liveness` swallows a corrupt queue file and
returns `{}`, so "we could not measure it" would have silenced the alarm exactly when it
mattered; only a **measured** 0 may. There is a third test arm for it.
