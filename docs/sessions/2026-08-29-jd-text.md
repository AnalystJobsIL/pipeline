Both steps green all four mornings, both `continue-on-error`, and the mail said nothing.
**Three causes, and the account was not one of them.**

### 1. The cooldown parked the FREE rungs, not the expensive one

One `_jd_attempted` date per url suppressed the native JSON GET, the plain GET and the Unlocker
alike for seven days. The todo was **13 of 13 parked on 08-27, 20 of 21 on 08-28, 18 of 20 on
08-29** — a 30-minute step doing three seconds of work and reporting a healthy zero.

A native GET is 0.24–1.02 s and a plain GET about a second; only the paid rung is worth a week.
`run_backfill(free_rungs_ignore_cooldown=True)` now walks a cooled row on the free rungs with
`bd=None` and counts it `paid_cooldown`. **The matched driver is unchanged** (default `False`),
because there the cooldown is not what is starving it.

The stamp thereby stops being a skip and becomes an **ordering** key — which is exactly what
makes a budgeted pass resume where it stopped instead of re-walking the same prefix every night.

I also wrote a `jd-all-cooling` alarm for this shape and then **deleted it**:
`test_alarm_for_speaks_for_every_zero_ish_run_and_stays_quiet_on_a_healthy_one` pins
`alarm_for(todo=17, cooldown=17) == ""` with the reasoning that an alarm which fires every
morning gets trained away. That decision is older and it is right; the defect was the cooldown
parking the free rungs, and it is fixed where it lives rather than reported on top of.

### 2. The Unlocker had never once rendered JavaScript

`Unlocker.__call__` posted `{zone, url, format: "raw"}` and nothing else, while
`validate_bd.py`'s own docstring says "the Unlocker renders JS". It does not unless asked.
Measured against the live account on HiBob's job page:

| call | bytes | text | carries the posting |
|---|---|---|---|
| `format: raw` (what we always sent) | 1,342 | **7 chars** | no |
| `"render": true` | **63,293** | 4,929 | **yes** |
| header `x-unblock-render: true` | 1,342 | 7 | no |
| `render + data_format: markdown` | 8 | 7 | no |

So every paid body this layer ever got back from a JavaScript site was the same shell the free
rung already had — which is precisely what `bd-shell` had been recording, unread, all along.
A page the free rung reads as a shell now renders on the first paid call.

**Rendering is slow, and wall clock is the real constraint** (credits are unlimited this month).
On the first archive pass, **nineteen consecutive rendered calls timed out at 90 s each** — 28
minutes for nothing — before `Unlocker`'s `failing-after-20` breaker opened and the remaining
candidates reported `bd-unavailable`. That is the breaker working, but one slow class of page
should not be able to end the paid rung for a whole run, so renders now carry their own budget
(`RENDER_CAP` = 60). Past it a shell is **skipped, not bought raw** — an unrendered credit on a
JS page returns the shell we already have — and the refusal is `bd-render-capped`, **transient**,
because it is our budget speaking and not a verdict about the page. Parking those for a week
would put the one class of page rendering is FOR permanently out of reach. Filed as **432**:
the cap is a guess and wants re-measuring after a week of real runs.

A host that returns `host_breaker` (3) empty bodies in one run is parked for the rest of it
(`bd-parked`) — Shopify has 33 cards on one SPA, Nebius 46.

### 3. The title gate decided what to KEEP

`_todo` now returns two pools. The TITLE pool is what the classifier could accept; the ARCHIVE
pool is every other Israel-passing card. Every card lands in exactly one counted bucket and the
driver asserts the sum. Measured on the committed cache:

```
2,141 cards -> 432 already carry a description - 28 title - 1,204 archive
447 refused as listing pages · 27 duplicate urls · 3 chrome · 0 dropped by the Israel filter
```

The title pool runs **first with the whole budget** — it is what the mail is made of, and the
archive is forty times its size, so ordering alone would starve it. The archive walks
`(oldest attempt, rank within company, label)`: a round robin that reaches every employer's
first card before any employer's second, because 287 of these cards are Comeet and a budget
that stops halfway must not have enriched two employers and none of the other 32.

**A listing page is refused in `_todo`, not in the ladder.** `run_backfill` stamps whatever it
walks, so a search url reaching the loop is parked for a week as if it had been read — and on
08-26 `careers.dhl.com/search-results?keywords=Israel` bought a credit. A native rung outranks
the url rule, so a Comeet or HiBob address is a posting whatever its path looks like.

**The Israel gate takes positive evidence only**, and I got that wrong first: `is_israel_job`
answers False for a card with no location at all, and my first version dropped those. A test
written for another purpose (`..._keeps_fetched_text_when_the_loop_dies`, whose fixture cards
carry no location) caught it. This driver fetches text; it does not judge relevance, and
`run.py` re-applies the real filter afterwards. `scrape_dropped_israel` is a **canary** — 0 of
2,141 today — not a filter.

## The cloud step

`.github/workflows/jd-archive.yml`, `30 1 * * *`, `timeout-minutes: 170`, work budget
`JD_ENRICH_TIME_BUDGET_MIN=90`, **no `continue-on-error`**.

**`concurrency: repo-state` is the load-bearing line, not the hour.** `daily-digest.yml` is
alone in its own group, so this job cannot delay the mail — and it writes `scraped_cache.json`,
which `scrape-refresh.yml` also writes, so sharing the group is what serialises the two. The
hour is nearly irrelevant: GitHub dispatched scrape-refresh at 04:44, 07:49, 05:41, 00:39 and
00:38 on its last five runs, and retry-unreachable at 09:14 on 08-29. So the pass assumes
nothing about running before the digest or after yesterday's run finished — it is idempotent
within a day and resumable across days by construction, and both are tested.

The timeout is a circuit breaker and the budget is deliberately smaller: `repo-state` already
carries scrape-refresh (78 min observed), retry-unreachable (50), auto-expand twice daily,
firmographics, listing-hunt, triage-dark and a 330-minute Sunday audit. Reserving 150 minutes of
a serialised group on an estimate is how a queue starves. **The first lap actually took 34.8
minutes**, so 90 has real headroom; raise it on the measured number (`scrape_archive_minutes`),
never on a guess.

## One thing I did NOT commit, on purpose

`cloud_state/pipeline_stages.json`. My local pass wrote an `enrich` stamp carrying all the
numbers above — and dated **2026-08-30**, because `run_backfill` stamps `dt.date.today()`,
which is the LOCAL date, and the run crossed local midnight while UTC was still 08-29.

`record_enrich` would then have treated tomorrow's 05:00 cloud drivers as a same-day
re-dispatch and SUMMED their flows onto mine: the mail would have reported ~960 fills and
nobody could have said what the cloud produced. The cache itself is the work product and is
committed; the stamp is a measurement of a local run and stays local. (The cards' own
`_jd_attempted` stamps are fine — 1,232 of them read `2026-08-29`, because the loop ran before
