## 1. `545@roles` — a retraction must bind to exactly one record

`cloud_state/roles_retractions.jsonl` is keyed by url, and `Retractions.match_all` was a
two-arm OR: the line's `role_id` equals the record's, **or** the line's address is the
record's own url **or any `seen_id` whose id half is a url**.

`percepto|senior product analyst` is `open`, `accept`, on the board, and genuinely in scope.
Its own url is the careers PAGE `https://percepto.co/careers/`; it also carries
`scrape:https://percepto.co/careers/data-insights-operations-ff-c6f/`, which is the OWN url of
`percepto|data insights operations` — a different posting, adjudicated OUT on 09-01. One line,
two records, and the second would have left the board, the mail and the dataset, published in
`meta.removed[]` under a reason describing a different posting.

**The preference belongs to the LINE, not to the record, and that is the whole design.** Asked
about `senior product analyst` on its own, that record owns no matching url — a per-record
"prefer my own url" rule falls straight through to its `seen_ids` and matches anyway. It is
also why the item's own note says keying by `role_id` does not escape it: `bind()` puts the
named record's url back into `_urls`, and the collision returns. So the decision is made once,
in `bind()`, where every record is in hand: each entry is stamped `_owned` when some record
claims that address as its own `url`, and `match_all`'s `seen_ids` arm fires only for a line
nothing owns.

**Measured on the committed ledger and the 38 lines at `aacaf94`:**

| | (line, record) pairs | lines matching nothing | lines matching >1 record |
|---|---|---|---|
| before `bind` | 38 | 0 | 1 (`…data-insights-operations-ff-c6f/`, if written) |
| after `bind` | 38 | 0 | 0 |

No existing line changed which record it takes and none stopped matching. The change can only
ever NARROW, and the only pair it removes is the one that was wrong.

The fallback is kept, not deleted. A posting whose record has since been re-keyed has no
owner, and its `seen_id` is then the only thing that names it —
`test_a_retraction_no_record_owns_still_matches_by_its_seen_id` is that case, and
`test_the_bounce_wrong_employer_retraction_withdraws_the_linkedin_row_only` and
`test_a_url_key_is_normalised_and_exact_never_a_suffix` both still pass unmodified.

With that in place, line 39 was appended: `percepto|data insights operations`, `withdrawn`,
reason from `docs/decisions/2026-08-30-quantitative-scope.md` (condition 5) and
`docs/decisions/2026-09-01-execution-is-not-an-analysis-output.md`. It takes exactly one
record. **The seam's own stored verdict for that row still reads `accept`** — the line is the
adjudication over it, and the reason string says so, because a reader of the public dataset
sees the reason and not this note.

## 2. The seen-id collision — a cycle guard that also skipped the drop

The 2026-09-02 mail: `roles seen-id collision (2 id(s) name two or more roles; worst:
discovery-linkedin:linkedin:4456923326 x2) — one of them will never be emailed`.

Both ids are one pair. `honeybook|product data analyst` (`superseded` into
`honeybook|senior product analyst` on 09-01, own url the LinkedIn card) and
`honeybook|senior product analyst` (`open`, own url the Ashby card) each carry
`ashby:9d5a89da-…` **and** `discovery-linkedin:linkedin:4456923326`, and both were last seen
2026-09-02. That is 2 colliding ids, which is the count the mail printed. The Fetcherr pair
shares ids too, but shares ONE url, which the predicate exempts by design.

**Yesterday's retitle-fold did cover this pair.** `superseded_by` is set and the 09-01 morning
check passed. What survived was the cycle guard wave B added to the twins block of
`_resolve_claims`: if any member's stored row is already `superseded`, `continue`. Right to
refuse a **re-election** — re-electing by today's source ranks once closed a supersede CYCLE
with the at-rest sweep, both halves off every product with `ledger N = store N` still green.
Wrong to abandon the **drop**: the loser stayed in `merged`, both keys were upserted, and
`id_collisions` — which `run.py` asks straight after `resolve_claims` — alarmed every morning
after, for a pair the ledger had already resolved, with one `filter_new` kill-switch across
two rows.

So the group is no longer skipped, it is **settled**: where every stored-superseded member's
`superseded_by` names one member of this same group and exactly one member is not
stored-superseded, that member takes the ids and the losers are dropped — with no election, no
`_supersede`, and no second `retitle folds` line, because the fold was logged on its own day
and the lane's own morning check says it is logged ONCE. Anything else keeps today's
`continue`.

**Verified on a copy of the committed store**, the two HoneyBook records reconstructed as this
run's cards:

```

              'honeybook|senior product analyst']
before: collisions ['ashby:9d5a89da-0e05-4e47-8ddb-57a186895cc1',
                    'discovery-linkedin:linkedin:4456923326']
```

### The three ways to get this wrong, each checked rather than assumed

1. **Closure.** A dropped loser is no longer upserted, so it could look absent. It cannot:
   `_record_run` iterates the sqlite rows, not `merged`, and its `status == "superseded"` arm
   `continue`s before any closure judgement. Asserted in the test.
2. **`filter_new`.** The survivor unions `aug[i]["seen_ids"]` — the STORED union, not just
   today's card — so nothing already delivered is offered again under the winner's name.
3. **Reclaim.** Untouched, and a same-company twin still never reclaims (`wc ==
   sup[k]["company"]`). `L.reclaimed == 0` is asserted in both new tests.

## 4. Dispensation — `558@registry`: the harness was handing a row its TWIN's mode

**The failing row had already moved before this session started.** On `aacaf94` the failure is
not `Synopsys Israel` at all:

```
FAIL night 12: pool repair_extract_gap (19:00 daily) lost 1 rows it should keep:
              ['Linnovate Technologies']
```

Same class, different row — which is itself the argument that `558`'s framing was one level
too shallow.

`worst` policy is DEFINED in this harness as *"triage re-classifies the row the same way
again"*, because a changed mode is a move between pools and the per-pool invariant assumes no
row moves. `_modes` was keyed by **`api_url`**, and that key cannot deliver the definition.

**My first write-up of this said "two rows share an address" and stopped there. That was the
smaller half, and an adversarial wave caught it before the push.** Re-derived independently:
**144 parked rows change their simulated `worst` verdict** under the fix, and only 5 of them
have an `api_url` at all.

| population | rows | what the old key did |
|---|---|---|
| no `api_url` | **139** | the guard was `if m and r[3]`, so they were never in the dictionary: `wrong-page` every night instead of their own mode (`no-url` 92, `url-dead` 24, `js-shell` 9, `page-empty` 6, `extract-gap` 5, `blocked` 3) |
| shares an address | **5** | gets its TWIN's mode — `Linnovate Technologies`/`Linnovate` and `GenCell Energy`/`GenCell` carry two different modes over one url; `Synopsys Israel` had none while `Synopsys` donated `page-empty` |

Either way the stub manufactured a mode CHANGE under a policy whose whole definition forbids
one, and the per-pool check reported a row the harness had itself moved. Keyed by the row's
own name — `triage_dark.main()` is the only caller of `classify` and always passes
`company=r[0]` — it is one line, and **the invariant is not touched at all**. **None of the
144 changes POOL**: three nights of `worst` seed 1 give byte-identical per-pool censuses under
both keys (`708/720/106/55/629/84/35/844/844`, orphans 0). Company names are unique across all
2,141 rows, so the new key cannot collide the way the old one did.

**And the class is not gone, only this cause of it.** A row whose own mode is `page-empty`,
held in the hunt pool by a `probe-woken` wake, still leaves that pool the night triage
re-stamps it and `_consume_wake` strips the wake — the same designed hand-off, now driven by
the row's own mode rather than a twin's. Exactly **1** row is in that state today (`Toyota
Connected`) and both keys give it the same mode, so nothing fires. The honest claim is that
the harness no longer invents the move, not that no designed move can ever be reported.
