## Two rules the operator set mid-session, and how they are enforced

**1. Nothing is recorded as having no roles, or as unreachable, without a hunt and an LLM read.**

`apply_proposals` complies by construction: it writes rows that assert PRESENCE and nothing
else. A name it cannot activate gets **no row at all** — not a park saying "no listing found",
which records a rung's 45-second reach as a fact about a company. Nothing is lost, because the
name stays in `research_companies.json`, which `listing_hunt.queue_targets()` works for 60
minutes nightly since `332`. Eight names took that path today, two of them carrying Israel
roles we cannot yet attribute (`Enlight Renewable Energy Ltd (ENLT)` 14 IL, `flō Optics` 1) —
those are unfinished, not empty. Guarded by
`test_the_applier_never_records_a_company_as_empty_or_unreachable`, which asserts no note
anywhere in the output contains "no listing found", "no IL listing", "unreachable" or "another
company", across four different gate verdicts, with a positive control.

**2. `unresolved` is not an end state, anywhere, including in the cloud.**

A board answering with ZERO postings is a row with a **wrong address**, not a company with no
roles — verified at the raw endpoints: Deel `{"jobs":[]}`, AI21 Labs `[]`, Run:ai
`totalFound:0`, Outbrain `meta.total 0`, and all four are hiring. Leaving such a row ACTIVE is
the worst of both: it produces nothing, and **no re-check pool can reach it**, because every
pool selector in this lane requires `r[4] == "false"`.

So `confirm_zero.ROUTING` exists only inside a run and is never written to a row. On the way
out the row is either given a verdict it earned or parked with `needs re-resolution` — a token
in `verdicts.TOKENS` **and** in `listing_hunt.HUNT_POOL`, so the 19:00 cron hunts it every
night until it has a real address. **36 rows took that path and all 36 are selected by
`in_hunt_pool`**, asserted *before* the write by `_assert_routed_rows_are_owned`, because the
pool token sits at the end of the segment and the 220-char cap truncates a tail.

## `confirm_zero.py` — the zero audit, and what it measured

59 native rows audited in full. **12 confirmed · 3 wrong-url parked · 1 zero-refuted ·
36 routed to the nightly hunt · 6 unconfirmed · 1 api-error.** Zero rows recorded as empty
without a hunt and an LLM read.

**A native row is judged by WALKING its board, not by asking it a question.** An
`israel_scoped` fetcher asks the board *for the word "Israel"*, and a 0 from that is a string
mismatch, not a census: all 24 Workday rows returned 0 for `searchText="Israel"` while their
boards held 11,000+ live postings. So every one was paged in full at `searchText=""` and every
posting judged by `pipeline.israel.is_israel_job`:

```
24 boards walked · 23 COMPLETE censuses (Capital One truncated at 1,200 of 1,841)
23 carry NO Israeli posting · Broadcom carries 2, both `ISR-Tel Aviv University`
```

That independently re-confirms `319@ats-fetch` a day later by a different method, and prices
it honestly: the `("Israel", "ISR")` patch is worth **one company and two postings**. Filed as
`376`. Broadcom is `zero-refuted` — an ACTIVE row with two Israeli postings the shipped
fetcher cannot see.

**The two verdicts that cannot become a zero.** `shows-none` (the page merely fails to show
roles) routes; only `states-none` (the page SAYS it has none) can confirm, and only when the
mechanical signals agree — a model reporting "states none" over a DOM full of postings is a
bad read, not a zero. A cap, a crash, a timeout or an LLM refusal all leave the existing note
untouched and report the row UNFINISHED: `confirmed` has exactly one reachable assignment.

## Six mistakes of my own, five caught before they shipped

1. **`registrable()` takes a HOST, not a URL.** Handed a URL it returns `"https"` — for every
   proposal — so the domain HOLD collided everything with everything and the applier wrote
   nothing while reporting each row as held. Caught by my own guard.
2. **The domain HOLD is meaningless on an ATS host**, where every tenant shares `comeet` or
   `greenhouse`. Not over-blocking at the margin: it refused the entire native path, which is
   the half that needs no scrape cache.
3. **`sys.modules["bd_rescue"] = None` poisons the interpreter.** It works as a lock and broke
   **77 tests** that import `bd_rescue` through `discovery_daily`. A lock whose blast radius
   is the interpreter is a landmine for whoever imports the module next. Removed; the note in
   its place explains why, because the next person will think of it too.
4. **A guard about not spending money made the ledger say money was spent.** My first BD guard
   set a plausible key *before* the imports and let the real `unlock_status` run: `SPENT["n"]
   += 1` sits one line above the request, so three tests incremented the counter and died on
   the missing `BRIGHTDATA_ZONE`. 0 requests, 0 credits — and `[bd-spend] bought 3` in the log.
   *(The line survives on pristine master and is `374`, filed for `infra`: it is not mine.)*
5. **I rendered the API endpoint.** `confirm_zero` first rendered `r[3]` for every row, and
   `r[3]` on a native row is JSON: `api.lever.co/…?mode=json` renders as 165 characters, so
   Leadspace, Hunters, Trullion and Aporia were one commit from being filed `shell`. That is
   exactly the failure the tool exists to stop, committed by the tool.
6. **My mass-zero guard fired on my own run, and it was measuring the wrong thing.** It
   compared `confirmed / judged` at 11 of 16. Rows that *cannot* be confirmed are routed away
   before the model sees them, so a high rate among survivors is by construction; against
   everything audited it was 11 of 59. The guard now measures the audited population **and**
   requires DISSENT — a model that confirms every row it judges and refuses none is not a
   judge. Corrected as a mis-calibration, with the reasoning, rather than a raised number.

**And one thing the yield gate got right by being wrong.** `drain_queue`'s first
`--min-yield` compared the run to the 488-name exhaust's 33% and aborted at 13.5%. That was a
mis-calibration — the exhaust's rate is `listing_hunt`'s, Playwright plus a search engine,
against HTTP-only rungs here — but the abort made me look, and the split it forced is the
better measurement:

```
replay 92/95 = 96.8%   (the GATE: names a previous night had already answered)
never-hunted 15/691 = 2.2%   (the MEASUREMENT: what the free rungs are worth on fresh names)
```

**2.2% is the number to plan with.** The free HTTP rungs are nearly exhausted over this queue.
