## The measurement (origin/master `27a0388`, 70 open roles)

The honest question is not "how long is the text" but "would our own parser accept it": that is
`extract_jd`'s pair of tests — `>= MIN_DESC` and `>= 2` marker families — asked of stored text.
It is now `jdfill.looks_like_jd`.

    open roles                        70
    text our own parser would reject  10        <-- the defect
      of those, no JD in them at all   4        Ballerine, TytoCare, Ecoppia, Zipher
    marker-family histogram           0:5  1:5  2:3  3:18  4:27  5:7  6:5

Two independent causes, both of them ours:

1. **`is_job_url` refused four real postings before a byte was fetched.** The `>= 3 path
   segments` rule (tightened 08-26, correctly, to stop search pages) refuses every company that
   publishes at `/careers/<role>`: `ballerine.com/career/ai-fraud-data-analyst-senior`,
   `tytocare.com/careers/product-analytics-manager`, `zipher.ai/careers/senior-data-analyst`,
   `jobs.techbiz.global/o/data-analyst`. Every one booked as `not-a-job-url`, for ever.
2. **"We already have the text" was `len(...) >= 300`, in all three selectors.** A character
   count cannot tell a JD from page furniture, and `scrape_universal._read_position_page` stores
   4,000 characters of page text with **no marker test at all**. So a Webflow nav bar and a GTM
   snippet cleared the bar and *locked the role out of the fetch that would have fixed it* —
   nothing ever re-examined a row that "had" a description. Ballerine's stored 3,999 characters
   were a product menu and a CSS block; the JD was never in them.

The two compound: (2) makes the row ineligible, (1) makes it unfetchable if it ever became
eligible.

## What changed

* `is_job_url(url, title="")` + `slug_names_title`. A two-segment path is a posting when its
  last segment **names the role we are fetching it for** (every slug word but at most one in the
  title, at least two hits — so `-il`/`-remote` is the one allowed miss). No new URL vocabulary
  to maintain. Measured over the 141 ledger rows: **9 admitted, all real postings**; the 3 still
  refused are Meta's `?offices[0]=` search URL (twice) and `port.io/careers`. Over the 987 cache
  URLs, handed the unrelated title "Data Analyst", it admits exactly the two that ARE
  data-analyst postings. `Item` gained a `title` so both backfills pass it.
* `looks_like_jd(text)` replaces the bare length test in `JDFiller.maybe_fill`,
  `enrich_scrape_jd._todo` and the matched driver's row filter (whose SQL got wider and cheaper;
  the JD test runs in Python, since sqlite can only count characters).
* **The write rule.** "Never shorten" is right between two JDs and backwards between furniture
  and a JD — Ecoppia's real description is 2,100 characters against 3,999 of Google Tag Manager.
  `enrich_matched_jd._store_text` and `roles.better_description` now prefer a JD to a non-JD and
  fall back to length only when both sides are the same kind.
* `_JD_MARKERS` gained `you should apply if` / `who you are`. Gong's greenhouse JD (4,536
  characters, complete) heads its requirements "You should apply if you have:" and reached only
  one family, so it was re-fetched every morning for ever. Measured over all 424 stored bodies
  (ledger texts + every `scraped_cache.json` card): promotes **exactly that one body**, no
  furniture.
* **Cross-lane, and it is load-bearing:** `roles.reconcile` had the same "longer wins" line. I
  repaired the rows, ran `open_sync`, and it handed the furniture straight back **and wrote it
  into sqlite** — the second sync could not tell the row had ever been fixed. `roles` owns
  `pipeline/roles.py`; please review `better_description`.
