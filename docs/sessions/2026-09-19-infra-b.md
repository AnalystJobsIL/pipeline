# 2026-09-19 — `infra` (b): the merge had the base all along and asked it one question

`644`, filed by `registry` this morning after finding its own previous session's work gone.
**Bright Data credits spent: 0. Seam calls: 0.** One lane change, in two commits.

## 1. What was actually wrong

`merge_csv_rows.merge(base, ours, target)` has taken the checkout base since 2026-08-22 and
used it **one-sidedly** — to decide which rows THIS run changed (`changed = [r for r in ours if
base[r[0]] != r]`) and never to ask what ORIGIN changed. So a row this run touched was written
wholesale, and "changed from a snapshot that is now three hours old" and "changed
authoritatively" were the same thing to it.

The 2026-09-18 night, from the commits and the run record:

| when | what |
|---|---|
| 21:23:18Z | `listing-hunt` run `35396505564` starts (`event: schedule`); its checkout carries Harel as `scrape,,www.harel-group.co.il/careers,false` |
| 00:08:04Z | `91b9676` (a `registry` session) activates `Harel Insurance & Finance` on `adamtotal` — 83 postings, **83 Israel** — and parks the Hebrew twin `alias-of` it |
| 00:25:12Z | the hunt hits `conflict on attempt 1: merging 11 paths onto 5dbec816`, applies **76** rows, pushes `7f960cd … (row-merged)` at 00:25:31Z |

Harel came out `scrape,,www.harel-group.co.il/careers,false` again, its `platform-fix
2026-09-19` segment evicted at the 220-char cap, and nothing anywhere said so: `check_invariants`
passes either way, because a parked row carrying a pool token is a legal row. Read-to-write
staleness at the merge itself was **19 seconds** — `persist_state` had fetched origin 3 s before
merging the activation away. That number is why the cheap alternative was rejected (clause 4).

## 2. What changed

`merge_csv_rows.merge` is a three-way merge. Same entry point, same call from
`persist_state.s_csv_rows`, no new module.

* **Per column** (`ats_platform`, `token`, `api_url`, `active` — all four; a token conflict is
  exactly the `adamtotal` shape): neither side moved → base; one side → that side; both to the
  same value → it; **both to different values → ORIGIN's**, with
  `::warning::merge_csv_rows: merge-conflict <row> <col> … origin kept` and the pair collected.
  A session writes with the later, fuller knowledge; a cron re-stamps the next night.
* **Per note segment** (`_merge_notes_threeway`): origin's cell is the starting point and every
  write goes through `pipeline.notes.replace_own`, so the cap is spent by the append-log's own
  rule — oldest UNPROTECTED first, never a slice, a terminal fact never taken — instead of by
  trimming theirs' tail, which is where origin's NEWEST segment lives. A segment ours deleted on
  purpose still stays deleted (`probe-woken` consumption, BACKLOG 15/60); a segment both sides
  rewrote keeps origin's and is reported.
* **A verdict about an address the row no longer has is dropped.** When origin moved `api_url`
  since our checkout, ours' `listing-hunt` / `dark-triage` / `queue-hunt` / `wrong-url` segment is
  dropped and reported `(address moved)`. The hunt's `no IL listing` was true of
  `www.harel-group.co.il/careers` and says nothing about the `adamtotal` board; carrying it over
  would re-arm a 14-day cooldown on a board nobody had read. (Orchestrator ruling on `registry`'s
  behalf; the 09-13/18 lesson that a ledger read is keyed by url.)
* **The conflict reaches a human.** `persist_state.log_merge_conflicts` appends one
  `{"kind": "merge-conflict", "rows": [...]}` line to `cloud_state/persist_log.jsonl` — after the
  merge loop, because the loop is what rebuilds that very file from origin — and
  `pipeline/run.py::_merge_conflict_alarms` turns records from the last **24 h** into
  `Stages:` clauses in the mail. No new stage key, no `ORDER` change, no workflow edit: a
  `stages.stamp` would have been overwritten by the night's next clean commit hours before
  anyone read it.
* `merge_json_cache` keeps the one-sided rule for its 13 keyed caches and now **counts** the
  both-changed keys (`CONFLICTS` + a `::warning::`). Filed as `646` with the per-path session-write
  counts and a re-measure date.

## 6. Clause 4

**Deleted or unified.** The `url-repaired` special case and its `kept_urls` counter are gone —
subsumed, because origin now wins every column it moved rather than only a column whose segment
named itself `url-repaired`. `_merge_notes`' base-aware deletion clause left the legacy union
too (it is unreachable there now). `report_deltas`' log-append became
`persist_state._append_persist_log(cwd, rec, who)` and the conflict record is its second caller,
so the cap, the atomic write and the one-record-one-line rule have one home rather than two.

**Extended, not duplicated.** `merge_csv_rows.merge` and `_merge_notes` (the same entry point
`s_csv_rows` already called; `grep -n "def merge" merge_csv_rows.py` still hits one),
`pipeline.notes.replace_own` (the eviction rule is not re-implemented here — the merge asks the
append-log to make room), `persist_state.report_deltas`' log writer, and `run.py`'s existing
alarm-reader shape (`_last_run_alarms`, `_receipt_alarms`). No new module, no new stage key, no
workflow edit.

**Rejected, on a number.** (a) *Fetch and re-merge immediately before the write* — that is what
`persist_state`'s rebase loop already does: it fetched origin **3 seconds** before merging Harel
away, so the window it would shrink (174 min → ~20 s) is not where the damage is; and the 09-12
pair shows 14 overlapping rows can occur in one night, so a 20-second window is not zero.
(b) *A tool whose snapshot row no longer matches origin SKIPS the row* (the item's cheap half) —
it would have lost the hunt's `Bulwarx` re-resolution, i.e. 14 of the 15 overlapping rows in 19
days are rows where the CRON is right. (c) *Failing the persist step on a conflict* — the step
resolves toward origin and stays green; refusing costs the night's whole commit for one cell,
and `check_invariants --strict` is still the gate that can stop a bad registry.
(d) *Giving `merge_json_cache` the same rule now* — 0 measurements of both-changed keys exist, so
`646` measures first; a rule nobody needs is a rule that can be wrong.

**Would the next session find this?** `grep -rn "origin-moved"` hits the merge's summary line,
the rehearsal's assertion and ARCHITECTURE §8 3c; `grep -rn "merge-conflict"` hits
`merge_csv_rows._conflict`, `persist_state.log_merge_conflicts`,
`run.py::_merge_conflict_alarms`, the §5 table row and `646`. Nothing still points at the old
rule: the `url-repaired` clause it lived in is deleted.

**Made harder.** (1) A fourth thing can now appear on the mail's `Stages:` line from
`persist_log.jsonl`, so that file is read by the digest as well as written by every commit.
(2) `merge_csv_rows.merge` returns a TUPLE `(applied + added, conflicts)`; a caller that expected
an int gets one silently wrong value (there is one caller and it takes the pair).
(3) `_ADDRESS_VERDICTS` is a fifth hand-kept vocabulary beside `_TOOL` — two of its four tokens
(`queue-hunt`, `wrong-url`) are not in `_TOOL` at all, so they key by `seg[:28]` and a rename
would silently stop dropping them. (4) `merge_json_cache.CONFLICTS` is module state a second
merge in one process overwrites; only `persist_state` calls it, once per path.
(5) Three existing mutation records (`merge-keep-remove`, `merge-trim-ours-head`,
`merge-slice-restore`) now anchor in the LEGACY (`base=None`) arm, which production reaches only
for a row BOTH sides added — `csv-note-append-unbounded` is the record that covers the eviction
rule on the path that runs nightly.
