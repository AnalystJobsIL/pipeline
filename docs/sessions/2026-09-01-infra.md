## 1. The jd-quality judge had no token — three mornings, silently

**Symptom.** `matched:jd-quality-unavailable(13 candidates, no verdict: llm-auth13)` in the
09-01 mail; `llm-auth9` on 08-31; `llm-auth7` on 08-30. In the SAME job, on 09-01, classify
reported `llm 372 (102 yes) ... failed calls 0; model claude-sonnet-5 x372`.

**Cause, from the runners' own env dumps** (run 33494404810, job 99813119785; run
33387229779, job 99472488706). The `enrich_matched` step's env block:

```
BD_RUN_CAP: 250 · DRY_RUN: · BRIGHTDATA_API_KEY: *** · BRIGHTDATA_ZONE: *** ·
MATCHED_JD_TIME_BUDGET_MIN: 20
```

No `CLAUDE_CODE_OAUTH_TOKEN`. The `Run the pipeline` step (line 259) and `firmo_drain`
(242) both carry it; the workflow-level `env:` carries only `BD_RUN_CAP` and `DRY_RUN`, and
GitHub injects no secret a step did not ask for. `pipeline/secretsenv.py` resolves
`<root>/secrets.env` on a runner, finds nothing, and returns `""` **silently by design**
(`secretsenv.py:24`), so nothing else could arm it. All 13 calls failed in ~10 s — instant
401s, not timeouts. This is **BACKLOG 448 in the mirror**: that was this same step missing
`BRIGHTDATA_*`, closed 08-30, and nobody checked the inverse direction.

**Why three mornings passed.** The refusal branch in `enrich_matched_jd._quality_pass`
printed nothing at all (`c["unavailable"] += 1; c["why:"+verdict] += 1; continue`), the step
is `continue-on-error`, and `docs/RUN_LOG.md`'s table of *every seam that spends the
subscription* had **no row for the jd-quality judge** — so the one document that would have
prompted anyone to check its step did not know the seam existed.

**Fixed.**
- the token on the step;
- **`llm-no-token`** as a distinct refusal. `pipeline/llm.py` reports 401 and 403 alike as
  `kind="auth"`, so `llm-auth` was telling three mornings to re-mint a token that was never
  sent (HANDOFF Open item 3 said exactly that, and is now corrected). `jdfill._refusal_kind`
  splits it in the `except LLMUnavailable` arm only — **not** as a pre-call check, which
  would have returned `no-token` on the runner before reaching the mock in
  `test_an_unavailable_model_leaves_the_cheap_verdict_standing` and gone red in CI while
  passing on every laptop;
- a **breaker**: the first refusal in `_SEAM_IS_DOWN` stops the calls, and every remaining
  candidate is still tallied **under the same reason string** — a distinct `llm-breaker`
  reason would render one outage as `llm-auth1+llm-breaker12` and break the
  `llm-authN`-is-a-count arithmetic the mail depends on. Transient kinds are deliberately
  excluded: one timed-out call says nothing about the next;
- a print on the refusal branch, worded without `description`/`_store_text` (an AST test
  forbids those literals in `_quality_pass`'s executed code);
- `test_every_llm_step_of_the_digest_carries_the_subscription_token`, over the three step
  ids that actually reach the seam. **Verified red with the token line removed.** The ids
  are listed, not derived: `enrich_scrape` and `stamp_enrich` import `pipeline.jdfill`
  without calling the seam, so an import-transitivity guard would demand the secret on
  steps that never spend it;
- the missing `docs/RUN_LOG.md` row, plus the sentence that a seam is only armed where its
  step is armed.

**N in `llm-authN` is a candidate tally**, not an errno — `matched_llm_candidates=13`,
`matched_llm_calls=13`, `matched_llm_unavailable=13`.

## 5. The debt this push owed, and the two sweep items

**BACKLOG 458, applied** (touching `persist_state.py` charges it, and the gate wants the
diff applied or cited). `merge_json_cache.merge`'s two deletion arms were asymmetric — ours

`test_the_merge_does_not_resurrect_a_key_the_origin_retired` pins all three arms.

**And the second thing the adversarial pass caught, which is the more important one.** I
filed `560` saying this fix "is NOT the same function" as `s_company_dict`'s and that a
deletion in those files "is only as durable as the next stale checkout." **Both false.**
`s_company_dict` has no rescue arm of its own — it *delegates* to `merge_json_cache.merge` —
so the one line I applied governs **thirteen** state files, not two: `scraped_cache.json`,
`firmographics.json`, `stale.json`, `queue_disposition.json` and the rest. I had taken the
larger blast radius, tonight, while filing an item that said it still needed measuring.

Worse: the unconditional rescue was **silently providing a mass-deletion guard for origin's
side**. `s_company_dict` refuses a run that dropped a quarter of the keys from OUR side
(CLAUDE.md rule 2), and `_keyed_list` has no guard at all — so with the rescue removed, one
workflow committing a truncated cache would have permanently deleted every key the other side
still held, with no alarm anywhere. The guard is now explicit and lives in `merge` where both
strategies get it: an origin that is empty, unreadable, or missing more than a quarter of its
keys is a broken run, not a set of deletions
(`test_a_broken_origin_is_not_a_deletion_of_a_quarter_of_the_cache`). `560` is rewritten to
say what actually happened, and what is still owed is the *measurement* — whether 25 % is the
right share for a 2,000-row scrape cache as well as for a 400-name queue.

Three documents said the merge "RESCUES a key the origin deleted", in the present tense, and
were true until this commit: `ARCHITECTURE.md` §2's retirement section, `queue_pipeline.py`'s
`retire_settled` docstring, and a test docstring. All three corrected in the same commit —
a stale sentence about merge behaviour is exactly what `458` cost the registry lane to learn.

**515's footnote → a guard.** GitHub honours the CI-skip marker anywhere in a message, body
included, so a commit that merely *names* it runs no checks: the commit that CLOSED 515 did
exactly that and had `total_count 0` runs while its parent had one. A prose rule already
existed, and the session that wrote it is the session that tripped it — which is why this is
now `check_no_ci_skip_marker`, pre-push only (the commit it catches is one no runner ever
sees). Cron state commits legitimately carry the marker and sit on origin, before the branch
base. The check's own file never spells the marker as one token.

**The HANDOFF caps move off the runners.** They exist against narrative accretion — a
weekly-scale failure — and CI is a per-push gate on a file with five concurrent writers. What
it actually caught on 08-31 was a race: three doc-only pushes red at **3,201 / 3,203 / 3,206**
words against a 3,200 cap (runs 33363762720, 33444708674, 33448417852), each because another
session's line landed between the local run and the push; each reddened master for every
other lane, over prose; each fix was another doc-only push minutes later. The third was

CI keeps the **shape** check: a missing section is nobody's race. `docs/AGENT_BRIEF.md`'s
enforcement table and `check_docs`'s own local-only paragraph were amended in the same
