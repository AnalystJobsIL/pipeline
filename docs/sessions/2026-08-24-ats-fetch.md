## What was measured and turned into code

**Eightfold has one public search, and `fetch_microsoft` was already using it.** The endpoint
behind every Eightfold careers page is `GET /api/pcsx/search?domain=<d>&query=&location=Israel
&start=&num=`; it answers unauthenticated on tenant hosts:

```
careers.qualcomm.com  domain=qualcomm.com   count=36  (31–36 requisitions per call, unstable pager; scrape row says 8)
apply.careers.microsoft.com                 count=14  (the old fetcher returned 10 of them)
paypal.eightfold.ai   domain=paypal.com     count=0   of 75 worldwide
jobs.dolby.com        domain=dolby.com      count=0   of 96
careers.lamresearch.com                     count=0   of ~1,325
```

So `fetch_microsoft` became `fetch_eightfold`; `microsoft` stays a key of the same function
because the store keys roles on `{ats_platform}:{job_id}` and Microsoft's public job page is
on another host. **A live paging bug came out with it:** the server pages at 10 whatever
`num` says (36 = 10+10+10+6), and the old loop advanced `start` by its requested 20 — so
it skipped positions 10–19 of every page. Microsoft had `count=14` on 2026-08-24 and the
old fetcher returned 10 of them, every morning; the new one returns 14 with the same keys
for the 10 (wave-1 payload review compared old and new on the captured page) — expect +4
Microsoft roles in the next digest. `standardizedLocations` ("Haifa, Haifa District, IL")
gives the explicit country code the Israel filter prefers over text.

**Phenom's search is `POST /widgets`** (`ddoKey: refineSearch`, `selected_fields.country:
["Israel"]`, `from`/`size`): GE HealthCare → `totalHits=20`, and an unfiltered walk (963 of
985 reachable; the server's sort is unstable, ~9 overlap per page boundary) found no
Israel-located job outside the facet, so the facet is exact; P&G / eBay / OpenText → 0 of
172 / 472 / 317, also exact; Dolby → 401. `fetch_phenom` raises on any response without
`refineSearch`, so a mis-pointed row is a failure, not a zero; it pages by what the server
returned, and it does NOT store `descriptionTeaser` (a ~350-char blurb that never states
years and would have cleared jdfill's 300-char "missing JD" bar — wave-1 payload review).

**Zero is a measurement for five fetchers.** Workday, eightfold/microsoft, phenom and
custom_json ask the board for Israel. They now carry `israel_scoped = True` as a function
attribute; `health.stale_reason` reads it off `FETCHERS` instead of a hand-typed tuple (which
named `custom_json` and `jazzhr` and not `workday`), and `platform_check` asserts the
behaviour (`stale_reason(p, "", 0, "empty", 0)`) rather than regex-parsing `health.py`'s
source. Effect on `stale.json`: 25 Workday `empty-board` rows leave the self-heal queue
and the 26th (Dell) re-enters it as a `fetch-error` with a reason.

**The one real fault in that group is now a named failure.** When a scoped fetcher's Israel
request comes back empty, `fetchers._whole_board_or_raise` asks the board for its total
once (Workday `searchText=""`, Eightfold `location=`, Phenom no facet); 0 raises
`fetchers.BoardEmpty("…: 0 postings worldwide — moved tenant?")` (Dell Technologies today:
`RAISED BoardEmpty dell.wd1.myworkdayjobs.com/External`; 83 live Workday tenants swept by
the wave-1 payload review raised for Dell and Dell Israel only). The probe re-raises a 4xx
(the endpoint is dead — that is the finding) and returns `[]` on 5xx / network / malformed
("could not tell"). **The first version swallowed every probe error** and so failed open on
exactly the condition it existed to detect — wave-1's sharpest finding.

**A rate-limit claim withdrawn.** One burst of ~30 Workday POSTs from this machine got HTTP
500 on the 14 tenants that followed; every attempt to reproduce it — including 25 POSTs at
10 threads in 3.2 s — answered 200. The first draft of §1 built "the loop stays sequential
on purpose" on that single observation; the rewritten §1 says what is measured (the loop is
7.0–7.2 min of per-row fetching ≈ 69 % of the pipeline step ≈ 26 % of the 27-minute job)
and hands the
parallelisation to `infra` as BACKLOG 83 with Workday's tolerance marked unmeasured.

**Board health reaches the mail.** `health.mail_lines(stale, previous)` → `- **Boards:**
new today: …; cleared: … · 2 fetch errors (Decart: HttpError: HTTP 404 …; Dell Technologies:
BoardEmpty: …) · 1 regressed to zero (…) · N empty (…) · 25 scrape rows on an ATS host`;
the delta against yesterday's `stale.json` comes first because the standing counts read
the same every morning (wave-1 health review); "cleared" is judged only over rows this run
scanned and never for an `empty-board` on a platform whose zero is a measurement — without
that, the first morning would have announced 30 boards "cleared" that were never broken
(wave-2 simulation); absent when everything was healthy. `Failed companies:` is capped at
eight names plus a count now that each carries its exception text.
`run.py` reads `health.previous()` before `record()` rewrites the file, puts the line in
`summary["fetch_health"]`, prints it as a `::warning::`, and the failed-companies line now
carries the exception text. `digest.py` prints it in the markdown, text and HTML audit
blocks; `docs/index.html` (public) renders none of it. A scoped run judges without writing
(`health.record(write=False)`).

**Smaller unifications in `fetchers.py`:** workable/breezy descriptions through `_snippet`
(junk filter + 6,000 cap) like every other fetcher; workable/breezy/bamboohr dates through
`_iso_date` instead of `[:10]`; `fetch_discovery` counts and prints its drops and keeps a
card whose slug names a DECLARED identity (`identity_facts`, exact whole-word match, 3+
chars — BACKLOG 9's second
half, narrowly; `check_invariants` runs the same predicate as a `warn()`, so nothing kept
here can block a digest); the module docstring documents `description` and the two
exceptions to "fetchers only fetch".
