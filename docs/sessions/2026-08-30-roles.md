## Where it flows from, without a session

The brief's clause 2 asks for three things by name.

- **Workflow:** `daily-digest.yml`, step `pipeline` (`python -m pipeline.run`) writes the three
  files; step `persist` commits them. **No workflow change was needed**, and that is the whole
  reason the artefact lives in `cloud_state/` — `persist_state.py`'s `--own cloud_state` is a
  directory and `expand_owned` runs `git ls-files -co`, so a new file inside it is committed
  automatically. `docs/` is NOT owned that way: `docs/index.html` and `docs/archive.html` are
  named individually, so a `docs/roles.csv` (which is what the brief asked for) would have been
  generated and never committed — a demo, not a dataset.
- **Cadence:** daily, `0 5 * * *` UTC. In practice GitHub drifts it badly — yesterday's digest
  fired at 11:32Z, and at 06:13Z today it had not fired at all — so the staleness alarm below
  is measured in run DATES, never in clock hours.
- **Alarm:** `Ledger._dataset_alarm`, on the bold `Stages:` line of the next morning's mail.
  It compares the meta file's `run_date` against `MAX(run_date)` in the sqlite `runs` log and
  says `roles dataset stale (roles.csv stamped X, last run Y)`, or `roles dataset missing`.
  It fired for real during this session's first scoped run against a scratch store that had no
  meta file, and went silent on the second run — which is the check proving itself in both
  directions rather than being asserted. A scratch store has an empty run log and is silent.

**Not yet proved unattended.** The first scheduled run that must produce a number is due

## The decisions, and what was rejected

**The window is on `last_seen`, and it is not a second answer to `_posted_in`.** The brief was
right to point at `pipeline/run.py:458` before choosing. `_posted_in` solves the EMAIL's
problem — "is this NEWS?" — which is why it leans on `posted_date` and refuses to call a
company's first-scan back catalogue fresh. The dataset asks a different question, "was this
role LIVE in the window?", and there `last_seen` is the honest axis: it is an observation we
made (154 of 154 records carry one) rather than a claim by an employer who publishes a date on
~5% of company-board postings. So `_posted_in`'s ladder is reused, but as DATA rather than as
a filter: `date_estimate` + `date_basis ∈ {posted_date (128), first_seen (2),
first_seen_oldest_for_company (13)}`, where the third value is the case `_posted_in` refuses
(and its NAME is the second version — see the adversarial waves below).
Rejected: a `posted_date` window (drops live roles and would have shipped 15 fewer rows for no
reason), and a `first_seen` window (the axis BACKLOG 309/310 removed from the mail for being
the day a cron happened to look).

**The description text is not in the CSV.** It is ≤6,000 characters per role with embedded
newlines. Two reasons, and the second is the one that settles it: naive parsers break on the
newlines, and **this file is committed to git every day, where history is unshrinkable**. The
CSV carries `description_len`, `description_sha1` (the join key) and `description_truncated`;
the text stays in `cloud_state/roles_text.jsonl` beside it, already committed and already
public. Measured cost of the decision: `roles.csv` is 143,223 bytes, against 514,587 for the
text file it points at.

**Skills are flattened twice, on purpose.** `skills` carries all of them on `;`, and eight
per-category columns (`skills_query`, `skills_bi`, `skills_de`, `skills_pa`, `skills_prog`,
`skills_method`, `skills_cloud`, `skills_lang`) let an analysis group by category without
parsing anything. The brief said five categories; there are **eight** — measured from
`roleprofile.SKILLS`: bi 27, query 21, de 18, pa 12, prog 9, method 7, cloud 3, lang 1. A test
asserts the eight columns cover the vocabulary, so a new category cannot silently drop skills
out of the file.

**The meta is a sidecar JSON, not a header comment.** A comment line breaks `pandas.read_csv`
defaults; a sidecar can carry per-column null counts and every enum's values in prose.

## Corrections to numbers in the brief

1. **`sent` does not disagree.** The brief reported 74 rows in sqlite `sent` against 69 truthy
   in `roles.jsonl` and asked which was right. Both are: 69 is per **role**, and the 74
   distinct seen_ids inside those 69 `sent` dicts equal the 74 sqlite rows **exactly, zero
   difference in either direction**. Seven ids appear in two records each, because a claim
   winner unions the loser's ids (`roles.py:663`). Nothing was fixed; a test now asserts the
   id SETS match, so the next person does not re-open it.
2. **Firmographics coverage is better than stated.** 110 of 116 companies join by exact name,
   but **113** join once `firmographics.identity_key` is applied. In the shipped CSV: 138
   exact, 3 identity, **2 unmatched** of 143 rows. The two are `Hila & Co.` and
   `Peak Innovation`; the third name the brief listed, `Tel Aviv`, is purged and not in the
   file at all.
3. **Truncation is not the store's to fix.** The brief offered "raise it with a reason, or
   record the true length beside the truncated text". Neither is available: the 6,000 cap is
   applied in **three** places — `fetchers._DESC_MAX` (`:42`, `:135`), `jdfill.DESC_MAX`
   (`:50`) and the store (`:723`) — and the first two run BEFORE the store, so the characters
   are already gone and the true length is unrecoverable for every row that already exists.
   Raising the store's cap alone would change nothing while implying the cap had moved. What
   is available is honesty: the literal is now `store.DESC_MAX`, and the CSV declares
   `description_truncated` for the 7 rows sitting exactly on it. The upstream cap is
   `jd-text`/`ats-fetch`'s call and is left to them.
4. **A purge had no reason field at all.** The brief asked for "a purge with a recorded
   reason" as though one existed. `roles.py:855` set only `status` and `closed_on`; all 7
   purged records (`Tel Aviv`, 2026-08-27) carried nothing else. `purge_reason` is now written
   — and written OUTSIDE the status transition, because a stamp on the transition alone would
   have left those seven reasonless for ever. That is not a backfill of something inferred:
   reaching that branch means the row is in `never_ours` **today**, so the reason is
   re-observed by the run that writes it. Verified 7 of 7 in a scoped run against a copy
   of the real store. **The COMMITTED ledger still carries 0**, and that is not a defect:
   the seeding pass ran only `backfill-seniority`, while `purge_reason` is written by
   `_record_run`, i.e. by a real run. The first scheduled digest writes all 7. Stated here
   because "all 7 now carry it" is what I first wrote, and it was true of my scratch store
   and false of the repository — which is the exact shape of failure this repo punishes
   hardest.
5. **`posted_date` 130/154 is unchanged and is not this lane's to move.** The asymmetry the
   brief names is real (present on ~100% of LinkedIn postings against ~5% of company-board
   ones) and it is a FETCH-layer fact: a board that publishes no date cannot be made to. What
   this lane can do is stop the missing date from being invisible, which is what `date_basis`
   does. The 15 undated rows in the CSV are labelled, not silently dated.

## The retention guard

`roles.dump()` now raises `LedgerShrink` if the write holds fewer records than the file it
replaces, and it is the single choke point — `Ledger.flush` and `stamp_sent` are the only
writers and both go through it. `flush` turns the refusal into a `Stages:` alarm and the day
still ships.

It is a **count** check on purpose. Every legitimate shrink-shaped event keeps the count: a
purge changes `status`, a supersede changes `status`, and `merge_duplicates` runs before
anything is recorded. A key-set check would have been stricter and would have fired on the
first legitimate `role_id` change.

What it does **not** cover, said plainly: the wholesale `cp -rT` restore path in
`daily-digest.yml`, which replaces both ledger files without going through this function at
all (BACKLOG 125 / 160). 160@roles stays open for that reason and is named in §7c.

## The adversarial waves

Two opus sessions, each in its own detached worktree at the checkpoint commit, read-only
against the tree and told to break the artefact rather than review it. Both were productive;
between them they found **eleven defects I shipped**, four of which would have been visible to
the public or would have cost a day of pipeline output. Every one is now a test.

### What they broke, and what changed

| # | defect | why it mattered | fix |
|---|---|---|---|
| 1 | `_ISO` matched the SHAPE only, so `2026-08-32`, `2026-13-01` and `0000-00-00` passed | `0000-00-00` is the standard MySQL/ATS null-date sentinel — one board away, not a thought experiment — and `_record_run` calls `fromisoformat` behind this predicate alone. Reproduced end to end: **one bad date froze the whole roles lane for the day** (no statuses, no closures, no episodes, no dataset) | `_iso` now parses the date. **This one predates my work**; the dataset only made it easier to reach |
| 2 | the shrink guard compared COUNTS | Two moves beat it: one unreadable line plus one absorbed role nets to zero, and a bare substitution never moves the count. ### The finding I want to single out

**`first_seen_backfill` was a label that overstated its own confidence, and it took an
attacker checking it against a different source to see it.** I derived it from
`min(first_seen)` over the roles at a company and then documented it as "the first day we ever
SCANNED this employer". Those are not the same fact: the ledger holds sightings of ROLES, not
scans of BOARDS. The attacker cross-checked all 13 labelled rows against the registry's own
notes and found **8 demonstrably false** — HiBob's row reads `re-audit 2026-08-21`, eight days
before the `first_seen` I was calling a first scan. The value is now
`first_seen_oldest_for_company` and says only what the ledger can know. This is the same class
of failure as the old root `SCHEDULING.md`: not a wrong number, but a **confident sentence
about a number**, which is the thing this repo punishes hardest.

### What I did NOT take from them

- **Hoisting `stamp_sent` out of `store.mark_sent`'s per-job loop** (measured by the attacker:
  ~11 ms per matching call, `O(emailed × records)` whole-file rewrites; ~1 s per emailed role
  at 50,000 records). Real, and irrelevant at 154 records — a 10-role cohort costs ~0.1 s. It
  changes `mark_sent`'s shape on the morning the dataset lands, which is the wrong morning to
  do it. Left as it is, with the measurement recorded here.
- **Making `write_dataset` atomic across the pair.** Two `os.replace` calls are not one
  transaction and I did not pretend otherwise. What I did instead is ORDER the window: the CSV
  lands first and the meta second, so a half-failure leaves the META stale — which
  `_dataset_alarm` detects and reports the next morning — rather than a stale CSV under a
  fresh meta, which nothing would catch.
- **`.tmp_` file leaked by `pipeline/atomic._swap` on a `BaseException`** (an Actions job
  cancel). `atomic.py` is shared plumbing, not this lane's file, and `persist_state`'s
  `_is_side_file` already excludes `.tmp_*` from staging, so it never reaches a commit. Not
  filed as a backlog item because it is a one-word change (`except Exception` →
  `except BaseException`) that the next infra session can make in passing; noted here so it is
  written down somewhere.
