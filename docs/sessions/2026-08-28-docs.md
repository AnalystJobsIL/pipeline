## What I changed

### 1. A census claim is one-sided, or it is not a claim

Full reasoning, the rejected options and the per-fact argument:
`docs/decisions/2026-08-28-census-facts.md`. In short:

| fact | was | is | choice |
|---|---|---|---|
| `active_rows` | `~900` (850–949) | `800+` | (a) floor |
| `registry_rows` | `1,300–1,500` | `1,300+` | (a) floor |
| `firmographics_profiles` | `~1,000` | the cell names `cloud_state/firmographics.json`; `Fact` deleted | (c) command |

The grammar: `800+` is the only legal form. A bare `875`, a bracket `~900`, a range
`850-950` and a malformed `~900+` are all errors. The two-sided forms are **refused rather
than discouraged** — leaving them legal leaves "just widen it" available, and widening is the
move that deletes the alarm while looking like maintenance.

Deleted with the bracket model: `precision()`, `_round_half_up()`, `bracket_holds()`,
`census_span()`, `_firmographics()`. One advisory constant replaces them,
`CENSUS_HEADROOM = 0.15`, which never decides whether a check passes — it only picks the
floor the linter *suggests* and the point at which it *warns* that a floor has decayed.

The floors were chosen from measurement, not taste. One snapshot per commit that ever touched
`companies.csv` — 111 of them, timestamps normalised to UTC: active rows 394 → 969,
largest rise **+140** in one commit, largest fall **−32**, largest drawdown **900 → 846 =
−6.0 %** inside **one hour** on 2026-08-23. `900+` would leave 7.1 % of headroom against
that; `800+` leaves 17.4 %. Registry rows 1,087 → 1,465 with a largest fall of **−13 rows**
ever (−1.2 %), so `1,300+` (11.3 %, 165 rows of slack) is ample and tighter than the
linter's own suggestion of `1,200+`.

**Four of those six numbers were wrong in the first draft of this session** and are corrected
here: `git log --reverse` order is not chronological in this repo (committer stamps mix
`+03:00` and `Z`), so the first script under-read the history and mis-ordered it. Re-derived
with `datetime.fromisoformat(...).astimezone(utc)` and a sort. The conclusion did not move
— every correction made the case for a floor stronger, not weaker — but the numbers did.

### 2. The registry describes itself

### 3. The morning-check archive is linted

`check_morning_checks` read `HANDOFF.md` and nothing else, so `docs/morning-checks.md` — where
every answered row ends up, and which three lanes wrote to on 08-27/08-28 — was checked by
nothing. The row parser is now `_morning_rows(doc_rel)` and both files go through it.
**Shape** is an error in both (five cells, an ISO date, a verdict a reader can check, and a
table header that is actually followed by a `|---|` separator rather than rendering as
prose). **Age** is checked only in `HANDOFF.md`: an archived row is history, and history that
can go red for being old is history somebody will quietly edit.

The cost of that asymmetry, named rather than left implicit: an UNANSWERED row moved to the
archive goes silent for ever. Probed against the real function, an archive row
`| 1999-01-01 | docs | the thing everyone forgot | — | |` produces zero errors and zero
warnings. The escape is not new — before today the archive was read by nothing at all, so
every archived row was silent, and this change narrows it — but it is the obvious way to
make a prediction disappear, and BACKLOG 361 should close it by allowing only an ANSWERED
row to be archived.

## The adversarial waves, and what they broke

Three Opus sessions were pointed at this change after it was written and green: one to attack
the grammar, one to mutation-test the guards, one to audit the blast radius and every claim.
They found **eight** defects between them, three of them holes in the thing this session
built. Every number below was re-derived here before it was acted on.

### The one that matters: `floor_holds` was dead code

`_fact_report` re-implemented the comparison inline instead of calling it, so
`floor_holds` — whose docstring says *"Defined in terms of census_floor so the tested function
IS the running one"* — had **zero production callers**. `test_a_floor_absorbs_growth_and_only_a
_collapse_breaks_it` pinned the boundary on a copy nothing ran, and both waves independently
flipped the live `>=` to `>` and watched the linter **and all 23 census guards stay green**.

That is precisely the sin the OLD `bracket_holds` docstring described — reintroduced, in the
same file, by the commit that fixed it. `_fact_report` now calls `floor_holds`, and two
guards hold it there: a source-text assert, and `test_a_value_exactly_at_the_floor_is_green`,
which drives `969+` against 969 through the real check.

### A floor could be LOWERED, silently

Setting all three `active_rows` sites to `0+` produced `docs check: 0 error(s)` and one
warning in a pile of six — and warnings do not touch the exit code. **Lowering a floor is
widening a band under another name**, and it was fully available. `floor_is_stale` cannot see
it: it is a decay detector and cannot tell `800+`-written-in-August from
`0+`-written-this-morning.

The linter now reads the **committed blob** (`_committed_token`) and errors on a lowering,
with one clause that keeps it from deadlocking: it is refused only while the OLD floor still
holds. If the number really collapsed, its own error fires and lowering is then the repair.

### `1,30+` parsed as 130

`_int` strips commas and the form check accepted any placement, so one deleted keystroke
dropped the registry floor tenfold, green. `1,,200+` was worse than green: it parsed as 1,200
and its near-miss produced the **COLLAPSED** message, which would have sent a reader hunting a
registry incident caused by a comma. A floor is now a canonically grouped, ASCII, non-zero
number and a plus — `٨٠٠+` (Arabic-Indic 800) was TRUE and unreadable at the same time,
because `\d` is Unicode-wide.

### And five smaller ones, all fixed

`suggested_floor(0)` returned `1+` — a floor ABOVE the value, in a message asserting "15%
headroom" — on exactly the mass-zero morning it exists for. The two live floors could compose
into a false coverage ratio (`800+` of `800+` reads as 100%; it is 66%). This commit added
three NEW hand-typed `800+` literals to unregistered prose, which is the failure the whole
file is arranged against; they now carry the FORM (`N+`), not a value. `900+100 rows` captured
`100` as a claim, so the lookbehind excludes `+` as well as the lookahead. And
`test_the_archive_is_checked_for_shape_but_never_for_age` pinned its asymmetry in one
direction only — it was the ONE guard of twenty that still passed against the pre-change
linter, because `errs == [] and warns == []` was already true when the archive was read by
nothing at all.

## The push broke the mutation gate, and the gate was already lying

The first push of this change (`4948be5`) turned `guard` green and its four safety steps ran
— and `mutation-gate` failed in **1m43s**, which is not its usual 45-minute timeout. The
message was:

```
baseline: HEAD is not a suite to mutate against (rc=0, 49 red) -- fix the suite first
```

`rc=0`. Pytest had **passed**. `tools/mutate.py`'s `_parse_failures` falls back to reading any
`<file>.py::<name>` line as a failed node id when a run names no `FAILED`/`ERROR` line — which
is precisely a GREEN run, and on a green run the lines with that shape are pytest's WARNINGS
SUMMARY. The fallback was systematically wrong exactly where it fires, and the number it
produced tracked the SIZE of the suite rather than its health.

Measured, both ends: **31** false matches at `21a8700`, **48** at this commit — this session's
21 guards all call `_cd()`, which execs `docs/check_docs.py` and brings the invalid-escape
DeprecationWarnings with it — against a `len(red) > 40` refusal. So this session tipped it
over. The gate had been hitting its 45-minute `timeout-minutes` for days (195/311), so nobody
had seen its baseline verdict since that threshold was written.

Fixed two ways, because either alone rots: `-p no:warnings` on every harness run (the false
source, at the root, ~200 times a sweep), and the fallback may fire only when the summary
actually says something failed — which still covers the case it was written for, a red run
that names no `FAILED` line, because such a run still prints "N failed".
`test_the_mutation_gate_cannot_read_its_own_warnings_as_failures` feeds the parser a real
green-run stdout with a warnings summary in it, and a real red one.

**`tools/mutate.py` is not this lane's file.** I edited it because this session's commit is
what tipped the count over, and leaving master with a gate that refuses to start is worse
than a reviewed two-part fix. Filed as **368** with the reasoning, the measurements, and the
two things I did NOT fix: the DeprecationWarnings are real and still there, and the
45-minute timeout is untouched — this lets the gate START, not FINISH.

**The `infra` lane found the same symptom an hour later** and filed it as **366**, attributed
to `docs`, which is right: `guard`'s own `pytest` was green on the same commit, and their
sharding work (`428f15a`) proved it was not the sharding either. 366 is closed in place by
368, in the struck-through form this file's header prescribes, rather than by a bullet in a
later section with the original left untouched — which is the shape the linter already warns
about twenty times. Their 367 ("seven mutations SURVIVE, and nobody has seen that since
2026-08-24") is the thing the gate could not tell anyone while its baseline refused to start,
and it is `infra`'s to answer.
