### 1. The Sunday audit could not search at all (silent, ~1 week)

`audit_empty_rows.serp()` was SerpApi-only, no fallback. Live account check:
`total_searches_left: 0`, `this_month_usage: 250`, Free Plan, resets 2026-09-01. So it

The first version of this warning fired spuriously on run one; that is why it counts.

### 2. Two activating pools could resurrect an `alias-of` duplicate

`verdicts.TERMINAL` is `defunct / domain-dead / duplicate of / redundant / recruiter` and
omits **`alias-of`** — a second row for a company already scanned at the *same board*.
`listing_hunt` and `deep_validate` spell the exclusion out themselves; `audit_empty_rows`
relied on `in_pool` and `crack_walled` had no terminal filter at all.

Both **activate directly**, and an alias row points at a board that *works*: the audit would
have searched, found that same board, verified it with real Israel jobs and re-activated the
duplicate — every eBay role published twice under two company names. `check_invariants`
check B (duplicate `company_name`) cannot see it: the names differ.

Pools: `audit_empty_rows` 260 → **255** (dropped `GE HealthCare Israel`, `eBay Israel`, and
3 recruiters), `crack_walled` 10 → **7** (dropped `Chakratec`, `GE HealthCare Israel`,
`eBay Israel`).

### 3. Three activation branches overwrote the whole notes cell

`audit_empty_rows:283`, `crack_walled:254`, `deep_validate:327` each did `fr[5] = "..."`
while flipping the row to active. That is the one moment you can least afford it: the
assignment deletes the terminal token that keeps the row out of the wrong pool and the
`dark-triage` mode that routed it there. All three now call `notes.replace_own`.

`test_every_note_writer_uses_the_append_log_helper` could not catch these — it looks for a
hand-rolled *trim*, and a whole-cell assignment does no trim. The new guard walks the AST
for `fr[5] = <not a call>`.

### 4. `repair_dead_urls` was one dry run from repairing an Israeli company to the CIA's cousin

Found by running it, not reading it:

```

```

"Imaging" and "Analytics", leaving core `dia`; `registrable("www.dia.mil")` is also `dia`;

bytes**, so `page_mentions_company` never ran — and the bot-wall branch accepts
`verdict in ("match","ats")` on the domain alone.

The `verdict()` weakness is shared plumbing (reported, not touched). The branch is ours: with
no page to confirm against, only the **whole** name is evidence, so it now requires
`registrable(host) == _norm(company)` (or an ATS host, where the tenant slug is already
checked). Verified: `dia.mil`/DiA rejected, `time.com`/Time To Know rejected,
`wix.com`/Wix and `fiverr.com`/Fiverr still accepted. Deliberate cost:

### 5. `crack_walled` was one `--apply` from moving Bancor onto The Bancorp Bank's board

Also found by running it:

```
[OK] 2/7 Bancor (icims): https://careers-bancorpbank.icims.com/jobs/search... -> 3 IL
```

Bancor is Israeli crypto (ex-Bprotocol). `careers-bancorpbank.icims.com` is a US bank. Both
identity gates passed: on a walled ATS the tenant lives in the **subdomain**, and

cracked-scrape branch now calls `page_mentions_company(..., strict=True)` on the listing
page before returning a verdict the write branch activates on — the same discriminator §3
already prescribes for a `weak` verdict, applied to "cannot tell". Measured three ways:

```

Bancor       on careers-bancorpbank.icims.com    -> False
Bancorp Bank on careers-bancorpbank.icims.com    -> True
```

activating — which is the state it was already in. `SCRAPE_VIA_UNLOCKER` (set in the
workflow) rescues the 403/405 hosts; without it the gate is stricter than it needs to be.

### 6. The two registry steps inside the digest had no time budget

`scan_dead_domains` (211 targets) and `probe_candidates` (181) run **inside the 05:00
digest, in front of the 05:45 email**, each with a 12s per-row timeout and nothing bounding
the loop — a 42- and 36-minute worst case. Every other tool in this lane is time-budgeted.
Measured normal cost: 37 rows in 30s and 35 rows in 30s, so ~2.9 and ~2.6 minutes.

Added `SCAN_TIME_BUDGET_MIN` / `PROBE_TIME_BUDGET_MIN`, **defaulting to 10** rather than 0,
so the protection is live without a workflow change (which is not this lane's to make) and
still leaves 3× headroom. Both stop cleanly and lose nothing: unscanned rows are re-tested
tomorrow (`_rescannable` is daily) and unprobed rows keep their baseline, because
`candidate_probe.json` only advances for rows a run actually read.

# Wave 2 — two adversarial agents took the commit above apart

`5505d3d` was reviewed by two independent read-only agents: one asked to propose additions,
one asked to break it. Nine findings were real. **Both of the wave-1 commit's headline
safety fixes had holes in them**, and the second agent found the more dangerous one.

## The two critical ones were in my own fixes

### C1 — the crack gate was a 24-hour delay, not a gate

`_page_names_company` correctly refused to activate Bancor onto The Bancorp Bank's board.
It returned `novrfy` to do it — and that branch does `fr[3] = got[1]`: it wrote the
**proven-foreign URL in as the row's address** and stamped `crack-walled …: host documented`.
`host documented` is a `probe_candidates` pool token *and* `listing_hunt`'s documented
fast-path token. So:

```
19:00 Mon  crack_walled  documents Bancor -> careers-bancorpbank.icims.com
05:00 Tue  probe_candidates polls The Bancorp Bank's page daily
19:00 Tue  listing_hunt fast-path scrapes the stored URL:
             il and not is_foreign(name, seed)  ->  is_foreign is False on an ATS host
             looks_like_a_job_listing_page      ->  True
           fr[4] = "true"
```

Same wrong outcome, one day later, attributed to `listing-hunt` instead of `crack-walled`.
The reviewer scoped it exactly: the other two blocked candidates (`Fintica`,
`Phoenix Financial`) *would* be caught by `is_foreign`, so the only population that leaks is
walled-ATS subdomain tenants — precisely the case the gate exists for, and the whole 25-row
crack pool. `listing_hunt` already refuses to persist a foreign URL, with a comment saying
why; the crack path now has a `notours` verdict that writes the note and never `fr[3]`.

### C2 — the DiA fix was one-sided

I hardened the 403 branch. The headline case is not `weak`, it is **`match`**:

```
DiA Imaging Analytics  https://www.dia.mil/dia-careers/  verdict=match  registrable=dia
                                                          _norm=diaimaginganalytics
```

and the 200 branch short-circuited on `match` before any page check. dia.mil was refused
**only because it answers 403**. The class is not small:

```
rows whose OWN url scores verdict 'match': 516
  of those, resting on a STRIPPED/partial core rather than the whole name: 125 (24%)
  e.g. Pecan AI/pecan.ai, Orca AI/orca-ai.io, Apple Israel/jobs.apple.com, SAP Israel/jobs.sap.com
```

So the safety property rested on a third party's bot wall rather than on any code here. One
rule now governs both branches, and a 403 tries the residential unlocker rather than
guessing from the domain.

### The gate was also far too strict to keep

Measured against ground truth — 60 rows the pipeline has already verified as that company's
own board — the first version returned False on **12**: Meta, Akamai, Ford, Microsoft
(Xbox), Microsoft Israel, Synopsys Israel, Sepio, Finaloop, Volkswagen (CARIAD), Greeneye,
Supersonic Studios, Estee Lauder. Three causes, each already a paid-for lesson in this repo:

1. a plain 403 to a urllib fetch (`Bit`'s own careers page) — the crack loop reached these
   with Playwright, so re-fetching with urllib is *weaker* evidence than what produced the
   candidate;
2. **strict TLS** — `scan_dead_domains.alive()` uses a lenient context on purpose, because
   "strict TLS on the scanning machine produced 6 false positives" (section 2). I
   re-introduced it;
3. `strict=True` wants the name's words consecutively, and **46 registry rows are named
   `... Israel`**.

Now: lenient TLS, unlocker whenever a key exists (not only behind `SCRAPE_VIA_UNLOCKER`,
which `audit-coverage.yml` does not set), a suffix-stripped retry, three-valued so an
unreadable page is *no evidence* rather than disconfirmation, and `continue` so one foreign
capture no longer abandons the company.

## M3 — the matrix that "cannot rot" shipped already rotted

`pools()` retyped each tool's filter, making it the **sixth** hand-maintained copy of the
pool definitions in a repo whose worst documented bug was three copies drifting. It was
wrong the day it shipped:

| pool | mirror | the tool | why |
|---|---|---|---|
| `triage_dark` | 270 | **242** | the copy omitted `SKIP_NOTES` |

deliberately parked duplicates). Now `verdicts.is_terminal() or alias-of`; orphans 5 -> **1**
(`SeeTree`, the one real one), and the alarm threshold drops from `>10` to `>0`.

## One ordering bug nobody had noticed

probe 05:00 -> triage 18:00 -> hunt 19:00. `probe_candidates._wake_note` strips the
`dark-triage` segment (that was the fix for the 105/105 inert-wake bug). Stripping it also
resets `triage_dark._needs_triage` to true, so the woken row is re-triaged **an hour before
the hunt**; a re-stamped `page-empty` then removes it from the hunt entirely
(`_actionable_mode` returns False for `page-empty` and `acquired`). The wake is not
recoverable — `probe_candidates` persists the new baseline *before* the wake test, so the
signal is spent. 6 of today's 181 probe targets already carry a `page-empty` stamp. Triage
now skips any row carrying `probe-woken`.
