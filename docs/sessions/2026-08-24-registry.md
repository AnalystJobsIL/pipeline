## The defects

### 1. The Sunday audit could not search at all (silent, ~1 week)

`audit_empty_rows.serp()` was SerpApi-only, no fallback. Live account check:
`total_searches_left: 0`, `this_month_usage: 250`, Free Plan, resets 2026-09-01. So it
returned `[]` **before making a request**, and phase 2 of the weekly audit — the rung that
finds boards which MOVED rather than broke — was a no-op across the whole ~255-row parked
pool. `resolve_broken._careers_url_via_serp` was given exactly this ladder on 2026-08-23
and it was never propagated.

Now SerpApi → `deep_validate.ddg` → `google_via_unlocker`. Measured after, SerpApi still 0:

```
Upsolver  4 urls: https://upsolver.com/
Cognata   4 urls: https://www.cognata.com/hiring/     <- an iCIMS row in the parked pool
Sproutt   0 urls
```

Before the fix all three were `[]`. When *every* rung comes back empty the tool now emits a
`::warning::` naming which credential is missing — but on the **rate** (10 attempts, 0
productive), not on the first empty result, which is about that company and not the ladder.
The first version of this warning fired spuriously on run one; that is why it counts.

### 2. Two activating pools could resurrect an `alias-of` duplicate

`verdicts.TERMINAL` is `defunct / domain-dead / duplicate of / redundant / recruiter` and
omits **`alias-of`** — a second row for a company already scanned at the *same board*.
`listing_hunt` and `deep_validate` spell the exclusion out themselves; `audit_empty_rows`
relied on `in_pool` and `crack_walled` had no terminal filter at all.

Both **activate directly**, and an alias row points at a board that *works*: the audit would
have searched, found that same board, verified it with real Israel jobs and re-activated the
duplicate — every eBay role published twice under two company names. `check_invariants`
check B (duplicate `company_name`) cannot see it: the names differ.

Pools: `audit_empty_rows` 260 → **255** (dropped `GE HealthCare Israel`, `eBay Israel`, and
3 recruiters), `crack_walled` 10 → **7** (dropped `Chakratec`, `GE HealthCare Israel`,
`eBay Israel`).

### 3. Three activation branches overwrote the whole notes cell

`audit_empty_rows:283`, `crack_walled:254`, `deep_validate:327` each did `fr[5] = "..."`
while flipping the row to active. That is the one moment you can least afford it: the
assignment deletes the terminal token that keeps the row out of the wrong pool and the
`dark-triage` mode that routed it there. All three now call `notes.replace_own`.

`test_every_note_writer_uses_the_append_log_helper` could not catch these — it looks for a
hand-rolled *trim*, and a whole-cell assignment does no trim. The new guard walks the AST
for `fr[5] = <not a call>`.

### 4. `repair_dead_urls` was one dry run from repairing an Israeli company to the CIA's cousin

Found by running it, not reading it:

```
[OK] 2/3 DiA Imaging Analytics   www.dia-analytics.com -> https://www.dia.mil/dia-careers/
```

`dia.mil` is the **US Defense Intelligence Agency**. How every gate passed: `_STOP` strips
"Imaging" and "Analytics", leaving core `dia`; `registrable("www.dia.mil")` is also `dia`;
`company_identity.verdict` returns a clean `match`. The page answered **403 with zero
bytes**, so `page_mentions_company` never ran — and the bot-wall branch accepts
`verdict in ("match","ats")` on the domain alone.

The `verdict()` weakness is shared plumbing (reported, not touched). The branch is ours: with
no page to confirm against, only the **whole** name is evidence, so it now requires
`registrable(host) == _norm(company)` (or an ATS host, where the tenant slug is already
checked). Verified: `dia.mil`/DiA rejected, `time.com`/Time To Know rejected,
`wix.com`/Wix and `fiverr.com`/Fiverr still accepted. Deliberate cost:
`ide-tech.com`/IDE Technologies is no longer auto-repaired **while bot-walled** — it still
recovers whenever the page answers 200 and `page_mentions_company` can confirm it. Re-run:

```
[--] 2/3 DiA Imaging Analytics   www.dia-analytics.com: no live careers page found
```

### 5. `crack_walled` was one `--apply` from moving Bancor onto The Bancorp Bank's board

Also found by running it:

```
[OK] 2/7 Bancor (icims): https://careers-bancorpbank.icims.com/jobs/search... -> 3 IL
```

Bancor is Israeli crypto (ex-Bprotocol). `careers-bancorpbank.icims.com` is a US bank. Both
identity gates passed: on a walled ATS the tenant lives in the **subdomain**, and
`company_identity.verdict` only checks a tenant in the **path**, so it returns the blanket
`"ats"` — which its own docstring defines as "we cannot tell" — and `is_foreign` reads that
as False. `_slug_matches("Bancor", "bancorpbank")` passes too, on plain containment.

The page settles it: it says "Bancorp" 18 times and `\bBancor\b` zero times. The
cracked-scrape branch now calls `page_mentions_company(..., strict=True)` on the listing
page before returning a verdict the write branch activates on — the same discriminator §3
already prescribes for a `weak` verdict, applied to "cannot tell". Measured three ways:

```
Wix          on careers.wix.com                  -> True
Bancor       on careers-bancorpbank.icims.com    -> False
Bancorp Bank on careers-bancorpbank.icims.com    -> True
```

A page we cannot fetch returns False, so the row keeps its documented-host state instead of
activating — which is the state it was already in. `SCRAPE_VIA_UNLOCKER` (set in the
workflow) rescues the 403/405 hosts; without it the gate is stricter than it needs to be.

### 6. The two registry steps inside the digest had no time budget

`scan_dead_domains` (211 targets) and `probe_candidates` (181) run **inside the 05:00
digest, in front of the 05:45 email**, each with a 12s per-row timeout and nothing bounding
the loop — a 42- and 36-minute worst case. Every other tool in this lane is time-budgeted.
Measured normal cost: 37 rows in 30s and 35 rows in 30s, so ~2.9 and ~2.6 minutes.

Added `SCAN_TIME_BUDGET_MIN` / `PROBE_TIME_BUDGET_MIN`, **defaulting to 10** rather than 0,
so the protection is live without a workflow change (which is not this lane's to make) and
still leaves 3× headroom. Both stop cleanly and lose nothing: unscanned rows are re-tested
tomorrow (`_rescannable` is daily) and unprobed rows keep their baseline, because
`candidate_probe.json` only advances for rows a run actually read.

### 7. `auto_expand.py` writes `companies.csv` with no `--apply`

Found the hard way: dry-running the nightly chain **appended two rows to the live
registry** — `Qualitest acq` and `Keter`, both on `secrethunter.io` aggregator URLs. Removed
them (1202 → 1200 lines incl. header; `check_invariants` clean).

Every other registry tool is dry-run until `--apply`; this one is the exception, and the
auto-expand workflow invokes it with no flags — so flipping the default from here would
silently disable the 08:00/20:00 cron. Added `--dry-run` and a startup banner saying which
files it will write; the proper flip (add `--apply` to the workflow *and* require it in the
script, one commit) is in `docs/BACKLOG.md` for the `infra` lane.
