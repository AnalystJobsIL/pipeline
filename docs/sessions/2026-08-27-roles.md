## What was wrong

### 1. A key that names sixteen different roles — and it was not on the backlog

BACKLOG 285 said `seen_id` carries no tenant and BambooHR ids collide. True, and re-derived:
over origin's 10 active bamboohr rows, 75 postings, 72 distinct ids, **3 colliding** —
`bamboohr:39` is both Bringoz's *Customer Success Director* and Miggo Security's *Senior
Backend Engineer*.

Designing the fix, I enumerated every active board to decide which platforms needed scoping,
and reported "workday: 571 postings, 552 distinct, **0 collisions**". An adversarial reviewer
read past my conclusion to my number and asked what the 19 missing ids were. They were not
cross-company. Re-measured:

```
Thales                        17 postings,  2 distinct job_id   ('Regular Employee' x16)
F5                             4 postings,  1 distinct job_id   ('0')
Aristocrat (Product Madness)   2 postings,  1 distinct job_id   ('Regular')
```

`fetch_workday` reads `bulletFields[0]`, a **tenant-configured display list**, not a
requisition number. `filter_new` passes a role only when none of its seen_ids is in `sent`, so
the moment one Thales role is emailed the other fifteen are suppressed **forever**. That is
five times the loss item 285 describes, on a platform where tenant-scoping fixes nothing —
the collision is inside one tenant — and my own audit had walked straight past it because it
counted only cross-**company** collisions.

`roles._strong_ids` accepted it too: it rejects `#`, `/` and `mailto:` — symbols, not words —
so all sixteen sat in one claim bucket with only `_titles_agree` keeping them apart.

### 2. The merge kept the best member and threw away the best field

`merge_duplicates` copied one canonical member wholesale and rescued only `posted_date`. The
canonical is elected on having an ISO date, and **scrape rows carry `posted_date: ""`** while
discovery cards carry a real one — so the card won, and both its short snippet and its
aggregator link shipped while the employer's own full JD was dropped in memory before
`upsert_matched`'s longest-text rule could ever see it. BACKLOG 260, 109 and 151 are one bug.

**109's stated mechanism is false** and that is why it survived: it says a later sighting
"does not replace `url` when the merge key matches". Both branches of `upsert_matched`
overwrite `url` unconditionally.

### 3. An outage would have reset every role's `first_seen`

`gap = run_date - last_seen > 3` calendar days cannot tell "we looked and it was gone" from
"there was no run". With no 08-27 digest, a resume on 08-30 gives all 76 open roles a fresh
`first_seen`.

### 4. `### Tel Aviv` shipped to subscribers, twice

`Tel Aviv` is a **city** that `listing_hunt` activated on `jobs.secrettelaviv.com`. Parking
the row stopped it being fetched but not being *alive* for one more day, and
`record_run`'s `judged` never named it, so its 7 records stayed `open` forever.

## What changed

**`store.seen_id`.** `{platform}@{tenant}:{job_id}` for `bamboohr, oraclehcm, eightfold,
microsoft, phenom`, plus `_is_id_shaped`, which refuses a value with whitespace or with no
digit and falls through to the url branch — **Thales 2 → 17 distinct keys**. The tenant is
derived from the posting's own url (`_tenant_of`), so no fetcher and no registry column
changed. `roles._strong_ids` refuses the same shapes.

**`merge_duplicates` is field-wise.** The canonical is elected on an identity of SOURCE, only
an address deeper than the board's own may be promoted or donate the url, and ONE donor
supplies both the link and the text. `_inherited` copies never donate.

**`upsert_matched` needs two answers.** `keep_first = mkey not in Ledger.closed_keys() and
missed_runs <= MISSED_RUNS`, where the store keeps a real **run log** — one row per date the
pipeline ran.

**`run.py`** computes `_origins` and `_never_ours` from the registry it already reads, and
`_alive` returns False for a company whose row is an aggregator. `record_run` marks those
records **`purged`**, not `closed`.

**The audit.** `python -m pipeline.store --audit-ids` asserts three things, the third being
the one this lane learned the hard way: no key from two companies, no board with two tenant
tokens, and **no board collapsing two of its own postings onto one key**. At run time
`Ledger.id_collisions` asks the same question of the run's merged list, format-independently.

## Four design decisions, and the measurement that settled each

**The tenant goes in the platform half.** My first rationale was wrong and is recorded as
wrong: I claimed it protected `roles._strong_ids`' junk-id guard. That argument is vacuous —
junk ids come only from the scrape lane, which is not scoped, and 51 of the 193 ledger
seen_ids already carry a colon in the id half. The real reason is
`enrich_matched_jd.sibling_urls`, which does `sid.split(":", 1)[1]` then `startswith("http")`;
`seen_id`'s fallback puts a url there, so a tenant after the colon would silently kill
`jd-text`'s whole sibling-JD rung for every role.

**The tenant rule was chosen by measurement, and my first rule failed it.** v1 (host + path
before the job id) gave 0 collisions but **21 of 56 boards yielded more than one tenant
token** — the Workday path carries the office, the Eightfold path a per-posting id. v2 cuts at
the first posting-marker segment: **56 of 56 boards, one token each, 0 collisions.** A
host-only rule was rejected on evidence too: Oracle HCM has shared SaaS pods (Verint sits on
`fa-epcb-saasfaprod1.fa.ocs.oraclecloud.com`), separated only by `sites/CX_…`.

**The authority gate is origin identity, not name matching.** I first proposed
`roles.names_in_url`. It is a NO-GO and the reviewer proved it:
`names_in_url("Bright Data", ".../jobs/fetcherr/.../data-analyst--tableau/...")` is **True**,
because the company token `data` matches the *job title* in the url slug. `names_in_url` was
built as tiebreak key 0 of seven among candidates already known to be the same posting; as an
admission gate on foreign content it fails, and it would have published Fetcherr's JD and
apply link under Bright Data's name. The gate is now `_same_origin`: same host and path prefix
for a scrape row, or the registry `token` matching a whole path segment for a native ATS
(token coverage is 133/133 comeet, 106/106 greenhouse, 52/52 ashby …). Verified on the eight
cases that decide it, including both Nift shapes.

**Only the aggregator class of parked row is purged.** My first predicate was
`company not in parked_companies()`. Also a NO-GO, also proven: `store._norm_company` strips
one trailing corporate suffix, so `TechBiz Global GmbH` → `techbiz global` → the **active**
row's identity, and **8 parked names normalize onto an active row** with 53 more parked as
`alias-of`. It would have closed a live role on the active row's own board. And `active=false`
conflates four facts — ~181 parked rows mean *we cannot read the page*, which is not a
closure. `Phoenix Financial` is the worked example: parked `js-shell`, but its Business
Analyst was discovery-verified on 08-26 and its registry `api_url` points at
**arizonafinancial.org**, an American credit union. The rest is BACKLOG 313.

## The adversarial wave, and the three things it stopped me shipping

Three Opus attackers, one lens each, against a disposable copy of the branch. Every finding
below was reproduced by hand before it was accepted; one was rejected with a measurement.
**Three of the four HIGHs were defects this session introduced.**

**The aggregator demotion published a competitor's JD under our name.** I had written "the
demotion comes FIRST because it can only ever demote, so it cannot promote a foreign address"
and used that sentence to justify applying it unconditionally. It is false: demoting one
member *promotes* another, and the promoted one was never tested against the registry. With
our own posting on LinkedIn and a competitor card on its own site — the `nift` shape, which is
in the committed ledger — the merge published `g-stat.co.il`'s url and its description under
Nift, **in both member orders**, and that was a regression against `origin/master`. The
demotion is gone; the canonical is elected on origin identity, which can only promote a member
proven to be on the company's own board.

**My headline test proved nothing.** `test_a_competitor_card_on_our_page_never_donates_its_
text_or_its_url` passed because both members sorted equal and `sorted` is stable — it was
asserting the order of two literals. And the real order is the reverse: `classify_grouped`
emits members longest-description-first, so the competitor's full card is member[0]. Every
merge test now runs both orders.

**A claim-winner flip re-emailed a delivered posting.** `resolve_claims` runs *before*
`upsert_matched` and unions only the run's fresh, in-memory seen_ids — never the loser's
STORED ones. So on a run where the key changed shape, the id the posting was actually emailed
under sat only on the loser's row and `filter_new` called it new. Its own docstring already
promised otherwise. One line.

**The ledger alone loses a live role.** `record_run` closes only where the fetch SUCCEEDED, so
a board that raises for four runs leaves its roles neither seen nor closed — and `keep_first`
would then pin a stale `first_seen` that `get_matched_since(cutoff_email)` can never return.
The role would not merely go un-alerted; it would be invisible to the email query. This is why
the store now keeps a run log rather than trusting the ledger by itself.

**The purge matched two different identities**, raw in `_alive` and normalised in
`record_run` — and normalising can only ADD names, whose only source is the ACTIVE twin of a
parked row. The registry holds eleven such twins. One set now, and it subtracts every identity
a live row answers to.

**`purged` did not keep a role out of the archive.** The archive is `matched` minus board and
never reads the ledger, so the seven `Tel Aviv` postings still published on `archive.html`
under the name of a city. My stated rationale for choosing `purged` over `closed` was
therefore false on the only product a reader sees. `_never_ours` is excluded from the archive
explicitly now.

Smaller ones, all fixed: a `+` in the fallback url split the `seen_ids` column and re-emailed
the role (and `_is_id_shaped` routes far more traffic onto that branch); `_tenant_of` broke on
the job id and on a marker word, so Fortinet's tenant moved with its own requisition number
and Dell's site — literally named `careers` — was swallowed, both degrading to the shared-pod
prefix; the token arm matched HOST labels, so `HiBob`'s own registry row certified every
tenant on the ATS domain it sells; url from one member and text from another published a Tel
Aviv posting's link with a Haifa posting's JD; and `id_collisions` exempted the worst case (a
shared key with no distinct addresses).

**One finding I did not take.** An attacker proposed widening `_never_ours` to rows whose
`token` is an aggregator address. Measured, that set is **40 companies** — Deloitte, Shufersal,
Zim, JTI, Phoenix Financial, Akamai — real employers whose `token` carries a repair-pass
fingerprint while `api_url` holds a real board. It would have taken their live roles off the
product, and it would have tripped the very mass-purge guard the same attacker asked for.
Filed as a limitation instead.

## A check that had been red for two days and nobody knew

`tests/rehearse_roles.py --golden`'s board check required
`(head - tree) == {the two collapsed doubles}` — which only holds while HEAD *predates* the
claim collapse. Once the feature was on both sides the difference became empty and the check
went red and stayed red. It fails identically on an **origin-vs-origin** run, two days after
the collapse landed, and nothing caught it because `--golden` is hand-run and not in CI. It
now asserts that the tree loses nothing HEAD had, and proves the feature RAN from the tree's
own board.
