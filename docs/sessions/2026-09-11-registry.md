## 1. The rename was the wrong fix, and the second declaration was already written

`roles._alias_fold_target` refuses any `companies.csv` name in any state as its first line,
so the standard recipe — park the row `alias-of X`, declare `ALIASES[x]` — is a no-op: the
parked name is still in `registry_names` and the declaration never fires. No log line, no
counter, nothing in the ledger says a fold was refused. That silence is why the class cost
three sessions to see (`522` Oak, `571` Investing, then six pairs in one morning).

A rename lifts the refusal, and `571` asked for one. Six renames would have been six
delete+adds, which `merge_csv_rows` resurrects on the next cloud merge (the 09-01 session
ended with three `Oak` rows that way), they would have thrown away names the employers
actually use, and they would have left the trap armed for occurrence #4.

What shipped instead: the row's own note already carries a dated verdict a human wrote —
`alias-of <R> <date>: <evidence>` — and nothing had ever read it. Now
`verdicts.alias_target` parses the survivor out of that segment, `run.py` builds
`{parked name -> survivor}` and passes it to the fold as `aliased`, and a registry name
folds only when **two independently dated declarations agree**: the note's `<R>` and an
`ALIASES` key naming the same row. `casefold` is not offered to a registry name — that
would make the exception "any parked row folds". Neither half alone folds anything, which
is the intended failure direction: prose can be truncated, and a curated map can outlive
the row it described.

Measured on the live registry: 64 of 64 `alias-of` rows parse (three predate the dated form
— `JPMorgan Chase`, `Unframe AI`, `Agency` — and are read by a second, undated pattern);
one target names no registry row (`Agency` → `Meridial`, which is correct and refuses
safely). Seven rows now fold; the vetoes that matter still refuse: `Meta Israel`, `Bounce`,
`Bounce AI`, `NVIDIA Labs`, `AppSec Labs`.
