## Where a rule lives is the decision

The tail cut belongs in `jd_body`, which every reader sees. The head cut deliberately does
not, and this is the part an adversarial wave would go for:

* `jd_body` IS the semantics of `looks_like_jd`, which decides `roles.text_quality` for every
  published row and `run`'s own publish gate.
* `roles.better_description` **returns `jd_body(...)`** rather than one of its two inputs — on
  purpose, it is what makes a tail repair hold — so a head rule there is a second
  head-SHORTENING path writing BOTH stores with none of `_reclean`'s floor or share ceiling.
  That is wave 2's shape: 13 rows, 39,956 characters restored minutes after being cut.
* A positional rule ("drop the next three lines") with one false positive would delete a real
  posting at every reader at once.

So `strip_head` runs in `extract_jd` and in `_reclean`, and `test_the_page_header_is_cut_at_
fetch_and_never_inside_jd_body` plus the mutation `jd-head-cut-moves-inside-jd-body` pin it
there.

## The one-off repair, and why it could not be a cron

96 rows re-cleaned, 11 re-captured from their own addresses, both stores written in the same
pass, proved stable across three further `Ledger.open_sync` runs. **The nightly `_reclean`
could not have done it**: the share was **39 %** against its 15 % ceiling, which exists
precisely so a furniture rule that has started matching prose cannot rewrite the store
unattended (CLAUDE.md rule 2). The ceiling was lifted as a module attribute for one attended
pass, never as a flag. After the commit the nightly share is ~0.

**The first sync reverted eleven rows, and that is the whole of `572` in one observation.**
The re-clean survived it — `better_description` returns `jd_body(...)`, so it reproduces the
tail cut — but every head repair lost, because the ledger's copy still had its header and was
therefore longer. The fix is the documented one: retract the ledger's stale line so the
repaired store is the only candidate, then re-install and sync. Runs two and three merged 0
and left both files byte-identical.

**And it took two rounds, not one — the second was found by checking the prediction I had just written into the morning-check row rather than trusting it.** After the first pass the chrome count was already 0, both stores agreed, and `open_sync` was stable across three runs. `_reclean` still found **20 rows and 6,900 characters**. The reason is the same sentence as `572`: `better_description` returns `jd_body(...)`, so it reproduces the tail cut but knows nothing about `strip_head` — and for the 85 rows I had re-cleaned but not re-fetched, no ledger line was retracted, so the ledger's copy was longer by exactly the header and won. The stores agreed on the text the cut had removed, and the nightly would have cut it again every morning for ever. A mass text repair is a FIXED POINT: re-clean, retract every line the cut shortened or the stores disagree about, sync, repeat until a pass changes nothing — asserted on three conditions (re-clean 0, `open_sync` merged 0, both files byte-identical). ## Traps this session hit, for whoever is next

1. **A bash heredoc mangles `\n` and `\\`** — three times today, twice silently producing a
   Python file with a real newline inside a string literal. Every patch script here is a FILE
   run with `python <path>`, not a heredoc.
2. **`docs/BACKLOG.md`, `tests/mutations.json` and the worktree's files are CRLF.** A
   multi-line anchor written with `\n` matches nothing, and `json.dump` over the whole
   catalogue rewrites 3,000 lines. Append textually, preserving the file's own terminator.
3. **`jdfill.native_jd` returns `(text, reason)`.** Treating it as a string raises inside the
   caller's `try` and looks exactly like the rung being unavailable.
5. **One `inspect.getsource` line makes the WHOLE test a source-text guard.**
   `tools/mutate._classify_killer` reads the test body, not the assertion, and
   `_STATIC_MARKERS` is `inspect.getsource` / `ast.parse` / `ast.walk`. Two of my guards
   pinned the behaviour in their first three lines and the SHAPE in their last one, and
   the shard reported `jd-head-cut-moves-inside-jd-body` as **killed ONLY by source-text
   guard(s)** and failed the gate — CI run 34610661040, `mutation-gate (3)`, 38 killed
   and 1 failed. The behaviour and the shape are two tests now. Check before pushing:
   `_classify_killer('.', 'tests/test_units.py::<name>')` must return `behavioural` or
   `direct` for every record's named killer.
6. **`git archive HEAD` is LF; a worktree checkout is CRLF.** A local script that verifies
   a record's `find` string matches must normalise, or it reports a catalogue that the
   harness will happily apply as broken — and it does so AFTER a rebase, not before.

4. **A mutation record can be born dead.** `jd-tail-rail-loses-its-hebrew-twin` SURVIVED its
   first killer: on the fixture the `Show more` pair cuts earlier, so removing the Hebrew rail
   changed nothing. Over the whole store there is no body with the rail and no earlier pair —
   the marker decides nothing today. It is kept for the posting LinkedIn does not fold, with a
   guard that exercises exactly that shape, and the comment says so rather than implying the
   marker is load-bearing.
