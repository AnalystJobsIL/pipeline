# 2026-09-01 — roles: the ruling reaches the board and the mail; one posting proven by its text

Extends `docs/sessions/2026-08-31-roles-b.md`. Two things the operator's audit surfaced, and
both were narrower in the code than they looked in the report. Every number below was
re-derived this session from the committed tree at `origin/master` (203 records, 157
published rows) or from a live read; the design was attacked by a fork wave before any of it
was written, and that wave changed three things.

## 1. The ruling was enforced on the dataset only — and only for STRUCTURAL blockers

`BLOCKED_POLICY = "exclude"` shipped on 08-31 keyed on `_blocker`, so a weak row with no
structural signal was "pending a fill" and still published. Two shipped that morning:
`Madanes Insurance Agency | Manager Bi` (`none` — no text at all) and `בנק דיסקונט |
אנליסט.ית אשראי…` (`snippet`). Both reached `roles.csv`, `docs/index.html` **and** the mail,
where `mark_sent` burned them in `sent` for ever. So the failure was two-layered: the
dataset's rule was too narrow, and the board and mail were never asked the question at all.

**The judge is now one function.** `roles.text_quality(desc, dlen)` — extracted from
`build_rows`' inline block, called from `build_rows` and from the role-selection block of
`pipeline/run.py`. The dataset keys its exclusion on `description_quality ∈ {snippet, none}`
instead of on a blocker; a weak row with no blocker counts as `pending` (unconditionally, at
detection, so a `mark` day reports the number it publishes) and leaves as `pending_excluded`.

**Measured on a copy of the committed store, both policy branches:**

| | rows | pending_excluded | blocked_excluded | quality | identities |
|---|---|---|---|---|---|
| `exclude` (shipped) | **157 → 155** | 2 | 1 | jd 155 · snippet 0 · none 0 · unmeasured 0 | all hold |
| `mark` | 158 | 0 (`pending` 2) | 0 | jd 155 · snippet 1 · none 2 | all hold |

With the fold in §2, the end state is **154 rows**, `excluded.superseded` 10 → 11, and every
published row `jd`.

**`unmeasured` still publishes, and that is the load-bearing distinction.** A stored length
whose text this export cannot see is a measurement failure — a frozen or corrupt
`roles_text.jsonl` — not an absent description. My first version of the helper collapsed the
two (`_int()` returns `""` for a missing length, which is falsy), which under `exclude`
empties the public file on a bad text day: the mass-zero failure class arriving dressed as a
policy verdict. Caught by four existing tests going red; fixed with an explicit sentinel and
pinned by `test_text_quality_separates_no_text_from_a_text_it_cannot_see`.

### The gate on the board and the mail, and the three orderings that make it a withholding

`_publishable` (board + mail) and `_mailable` (mail, adding the title check). Three
constraints, each of which was a real bug when I got it wrong:

1. **Before the payload.** `out/digest-<date>.json` is built from `email_jobs`, and
   `mark_sent` burns every row in it. This is also a pre-existing bug the gate fixes:
   `digest.build_markdown` has always hidden a mangled-title card from the mail BODY, and
   `email_jobs` carried it into the payload anyway — every card blob the board ever hid was
   marked delivered and `filter_new` never offered it again. `rolecard.is_mangled_title` is
   now one predicate; the mail refuses such a role at SELECTION while the board still hides
   it at render and still says so on the `Render:` line (that alarm is `scraper`'s and stays).
2. **After `alive_jobs`.** A role held for having no description is still OPEN. Gating
   before the closure snapshot tells the record it left its board.
3. **The archive is `matched` minus what is ALIVE, not minus what was RENDERED.** This one
   I found by breaking it: the first version filtered `board_jobs`, and `onboard` is derived
   from `board_jobs`, so a held role fell into the archive — published on a page headed "no
   longer on the employer's careers page" while it is live. The comment there always said
   `# = still open`; the set finally is. It also fixes the same latent bug for anything the
   `BOARD_MAX_ROLES` backstop trims.

**Re-admission.** A held role is stamped `held_since` and re-offered to the mail for
`EMAIL_READMIT_DAYS` (4) once its text lands, regardless of the 48h `posted_date` window it
has meanwhile fallen out of. **The stateless version was rejected on a measurement, not a
preference:** keying the re-offer on `roles_text.jsonl`'s `updated` needs no new field, and
the golden rehearsal caught it emailing roles nothing had ever held — `jd-text` backfills
descriptions nightly, so that rule quietly mails the unsent backlog under a heading
promising the last 48 hours. Widening that promise may well be right; it is BACKLOG 310's
call, not this ruling's. (The fork wave had recommended stateless; the rehearsal outvoted it.)

## 2. Nestlé / אסם — one posting, two employers, and no bucket that could see it

`Nestlé` and `אסם` published the same posting twice: byte-identical descriptions (971 chars,
one `desc_sha1 8dbd857f…`) under the same title, at two Indeed `jk=` addresses. `_groups`
buckets on strong seen_id, raw url and posting key; the ids differ, the urls differ, and
`_pk` is `''` for both because they are aggregators. **The pair was in no bucket and was
never pair-tested** — `same_posting` was never even asked.

The generic fix is a fourth bucket and one narrow arm, cross-company only:
`_same_text_posting` — identical `desc_sha1` over `SAME_TEXT_MIN` (200) characters, and
normalized titles EQUAL (not merely agreeing: the location-glue and seniority bypasses lean
on an address we can see, and here there is none). `same_posting` itself is untouched, so
`same_role_twin` cannot reach the text arm and a same-company byte-identical pair — one
careers PAGE stored as several rows' text, BACKLOG 370 — stays exactly as unfolded as it was.

**Byte equality, never a normalization.** Mobileye's `Business Analyst` and `Forecast
Analyst` are two real openings whose 2,835-character texts differ in **eight** characters
(offsets 35–44). Any casefold, whitespace-collapse or n-gram comparator folds them and
deletes a live role. Pinned as a refusal fixture.

**A record's key is its STORED `desc_sha1`, never re-hashed.** `flush` strips the in-memory
description and `_open_sync` re-seeds it from `roles_text.jsonl`, so on a frozen text day
every record's `description` is `""` while `desc_sha1` still names its text exactly.
Re-hashing keys those records on the hash of nothing and silently stops pairing anything.

### The winner was wrong, and wrong as a class

`_winner` would have crowned **Nestlé** — a PARKED registry row — over `אסם`, which is
active. Both fail `names_in_url` (`indeed`/`com` are plumbing), both are `discovery-indeed`
rank 2, neither is incumbent, so the election fell through to the *lowercase-stub* key:
`name == name.lower()` is TRUE of every name in a caseless script, so `אסם` read as a
"kornit"-shaped stub. That is a systematic defect for every Hebrew, Arabic and CJK name in a
cross-company group. Two fixes:

- the stub key now requires case to exist (`name != name.upper()`); the kornit/Kornit
  Digital election is unchanged;
- a new evidence key after `_source_rank`: **the company the posting itself names**
  (`_name_in_text`). The אסם posting opens "קבוצת אסם סחר מגייסת…" and names אסם twice while
  never naming Nestlé.

`_name_in_text` reads RAW whitespace tokens, requires EVERY token to appear as an exact
token, and refuses an empty token set outright. Both refusals are measured, not assumed:
`_identity_tokens` returns **nothing** for 16 registry names and 2 role companies (`HP`,
`F5`, `3M`, `EY`, `AT&T`, `D-ID`, `DT`) and `all()` over empty is True — the BACKLOG 510
shape, free evidence for the names least able to prove anything. And one token of a two-word
brand is a coincidence: `names_in_url("Bright Data", …/fetcherr/data-analyst/)` is True
because `data` matched the job TITLE (BACKLOG 260). Edge punctuation is stripped — my own
test caught `"We are Meta."` tokenizing as `meta.` — but only at the edges, so `ex.co`,
`at&t` and `d-id` keep their insides.

**Verified on a store copy:** `open_sync` over the real 203 records changes **exactly one**
record — `nestl|…` → `superseded_by` `אסם|…`. Nothing else moves. Armis/OTORIO (the only
other sha1 collision in the store) is already superseded and excluded from the sweep. The
fold lands via `sweep_store`, not the run-time arm: per-run discovery cards do not carry the
enriched JD, so the run-time arm is forward defence only.

## A correction to the record: there is no mojibake

Two exploration passes reported that 11 of 203 records carry cp1252-mojibake company/title/
text, with `desc_sha1` computed over clean text — and I had a backlog item drafted for it.
**It is false.** Reading the files with an explicit encoding shows `roles.jsonl`,
`roles_text.jsonl` and `roles.csv` are clean UTF-8 throughout, and `sha1(text)` equals the
stored `desc_sha1` exactly. The mojibake was an artefact of my own shell reads on Windows
(the cp1252-stdout trap this repo already documents). Two docstrings I had written on that
false premise were rewritten before the commit, the backlog item was never filed, and this
paragraph exists so the next session does not re-derive the same wrong finding.
